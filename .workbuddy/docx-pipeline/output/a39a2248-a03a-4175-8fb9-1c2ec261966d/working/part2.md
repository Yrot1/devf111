## 第3章 系统需求分析

### 3.1 系统设计目标与可行性分析

#### 3.1.1 系统设计目标

本系统的总体目标是：面向软件研发协作场景，构建一个能够连接代码仓库数据、理解研发上下文、提供带证据分析建议的智能协作系统。具体目标包括：

（1）数据连通性。打通代码仓库中缺陷、合并请求、持续集成、代码与文档等多源数据，建立统一的本地数据底座，使分析活动不再依赖人工跨平台收集信息。

（2）分析专业性。针对缺陷分诊、合并请求审查、持续集成排障三类高频任务，分别设计专用的分析智能体，输出分类、优先级、风险点、修复建议等结构化结论，而非笼统的问答回复。

（3）协作系统性。对"版本能否发布"这类需要跨领域综合的问题，提供多智能体协作机制，由规划、执行、观察、综合等角色分工完成分析，并显式处理证据缺口与结论冲突。

（4）证据可溯源。所有分析结论必须附带证据来源（代码位置、缺陷编号、日志片段、文档引用），检索范围按仓库隔离，检索不到证据时如实说明而不是编造。

（5）执行安全性。系统对涉及外部系统写操作（如提交评论、创建缺陷）的能力采用"草稿—人工确认—执行—审计"的安全流程，保证智能体具备执行能力但不越权。

（6）效果可度量。建立固定评测集与量化指标体系，回答质量可测量、改动效果可回归对比，为系统持续迭代提供依据。

#### 3.1.2 可行性分析

技术可行性方面，系统所依赖的大语言模型经 OpenAI 兼容接口接入，可灵活切换；后端 FastAPI、数据层 PostgreSQL 与 Milvus、编排框架 LangChain 与 LangGraph、前端 Next.js 等技术均有成熟的社区生态与文档支持；工具调用、SSE 推送、结构化输出等关键机制均有标准的实现范式，技术风险可控。

经济可行性方面，系统全部基于开源组件构建，基础服务均可通过 Docker 在单机环境部署；大语言模型与嵌入模型的调用成本与使用量成正比，在开发与中小团队使用规模下成本较低；系统不依赖专有商业组件，具备良好的经济性。

操作可行性方面，系统以 Web 应用形式呈现，提供仓库管理、对话、分析结果、评测等图形化页面，研发人员无需了解内部实现即可使用；同步、分析、评测等操作均可在页面一键触发，交互成本低。

### 3.2 功能需求分析

根据研发协作的实际场景，系统功能需求可归纳为以下十一项，如表3-1所示。

**表3-1 系统功能需求汇总**

| 编号 | 功能名称 | 功能描述 |
|------|---------|---------|
| FR1 | 仓库接入与数据同步 | 连接代码托管平台仓库，同步缺陷、合并请求、变更文件、评审评论、持续集成运行记录与日志，支持首次接入少量取样与全量同步，报告同步覆盖范围与状态 |
| FR2 | 仓库健康全景 | 汇总仓库的缺陷、合并请求与持续集成状态，生成项目健康摘要，检查数据完整性与时效性，数据不足时明确提示 |
| FR3 | 缺陷智能分诊 | 分析缺陷的分类、优先级、复杂度，推荐负责人，提取行动项与重复候选 |

| FR6 | 多智能体协同决策 | 对跨领域工程问题进行任务规划与多智能体分工分析，检查证据缺口与结论冲突，汇总形成统一决策建议 |
| FR7 | 知识检索与问答 | 管理知识库文档，提供向量与关键词混合检索、重排、引用标注、召回测试与问答能力 |
| FR8 | 上下文与记忆 | 长会话上下文压缩与摘要，会话内容封存沉淀，候选记忆经人工批准后跨会话复用 |

| FR10 | 安全草稿 | 对评论、创建缺陷、添加标签等写操作先生成草稿，经人工确认后执行，并记录审计日志 |
| FR11 | 系统评测 | 基于固定评测集与 RAGAS 指标对回答质量进行量化评估，支持回归对比与失败诊断 |

下面对核心功能需求做进一步说明。

（1）仓库接入与数据同步（FR1）。系统需要支持用户填写仓库地址与访问凭据完成仓库接入，并按分页方式从代码托管平台同步数据。考虑到大仓库全量同步耗时较长，首次接入应支持仅取少量记录进行快速体验；正式同步与定时同步则默认读取全部分页，并允许设置每类记录的总数上限。同步完成后需要向用户报告实际覆盖范围，状态需区分"完整完成""请求成功但为空""达到数量上限或部分失败""全部失败"与"未选择数据源"五种情形；部分失败时应保留已有明细数据，不更新最近成功同步时间，避免将不完整数据误认为完整快照。

（2）缺陷智能分诊（FR3）。输入为缺陷标题与描述（以及关联的历史证据），输出包括：缺陷类型分类（如功能缺陷、性能问题、文档问题等）、优先级建议、复杂度评估、负责人推荐、可执行的行动项列表以及可能的重复缺陷候选。输出采用结构化 Schema，保证可以被页面稳定渲染。

（3）合并请求风险审查（FR4）。输入为合并请求的变更文件与补丁内容，结合关联缺陷与历史评审讨论，输出变更摘要、关键变更说明、风险点列表（包括安全、鉴权、数据一致性等高风险路径的识别）、审查检查清单、测试建议以及"建议合入/暂缓合入"的决策建议。

（4）多智能体协同决策（FR6）。以"检查当前缺陷、合并请求与失败的持续集成，判断该版本是否可以发布"为典型用例：系统首先由规划智能体生成执行计划（包含任务清单、任务依赖与验收标准），用户确认后由调度器按依赖关系并行执行各分析任务（仓库状态检查、缺陷检查、合并请求检查、持续集成检查等），随后观察智能体检查各任务输出中的证据缺口、结论冲突与需人工确认事项，最后由综合智能体汇总形成统一结论。工作流执行过程与各智能体的输出需要完整记录并可在页面回看。

（5）知识检索与问答（FR7）。系统需要提供知识库管理（创建、上传文档、解析与索引）与检索问答能力。检索需要支持向量与关键词双路召回、融合排序、重排与分数阈值过滤；回答需要附带编号引用，明确标注证据出处；当检索不到足够证据时，系统应如实提示而不是给出无依据的回答。此外，提供召回测试能力，输入查询语句可直接查看各候选块的得分与排序，用于诊断切分与检索配置问题。

（6）安全草稿（FR10）。对涉及外部系统写操作的能力（如对合并请求发表评论、创建缺陷、添加标签），系统不允许模型直接执行，而是先生成操作草稿，包含操作类型、目标对象、拟执行的正文内容与风险级别；草稿经人工确认后方可执行，执行结果与失败原因写入审计日志。

### 3.3 非功能需求分析

（1）安全性需求。访问凭据（如代码托管平台令牌）仅通过环境变量或用户输入提供，持久化时必须加密存储，日志中不得打印令牌明文；写操作必须经过草稿与人工确认流程；系统需记录关键操作的审计日志；检索与问答必须按仓库隔离，防止跨仓库数据泄露。

（2）性能需求。同步接口需支持分页与数量上限控制，避免大仓库同步阻塞服务；对话链路的模型推理耗时较长，需通过流式推送保证用户可感知的响应性；多智能体工作流需为单任务设置超时上限（本系统取 90 秒），避免个别任务挂起拖垮整个工作流；上下文需要设置 token 预算（本系统默认输入上限为 24000 tokens），保证长会话不超过模型窗口。

（3）可观测性需求。每次对话需记录工具调用序列、引用来源与最终回答；多智能体工作流需持久化工作流级与任务级运行记录（含耗时、成功/失败/跳过统计、重规划次数等指标）；关键链路需输出结构化日志，便于定位"工具参数错误、检索证据不足、任务结论冲突"等典型问题。

（4）可扩展性需求。系统需提供标准化的工具扩展机制，支持通过模型上下文协议（Model Context Protocol，MCP）接入外部工具服务；支持将稳定的操作流程沉淀为技能（Skill）并在任务中按需激活；多智能体工作流的任务类型应可注册扩展，新增分析能力时无需改动调度框架。

（5）可用性需求。前端页面需覆盖仓库管理、对话、分析结果、评测等主要功能；长耗时操作需展示执行进度（规划、工具调用、任务进度）；错误信息需以用户可理解的方式呈现，并给出恢复建议。

### 3.4 本章小结

本章首先明确了系统的六项设计目标并对技术、经济、操作三个维度的可行性进行了分析；随后梳理了十一项功能需求，并对仓库同步、缺陷分诊、合并请求审查、多智能体协同决策、知识检索问答与安全草稿等核心需求进行了详细说明；最后从安全性、性能、可观测性、可扩展性与可用性五个方面提出了非功能需求。本章的需求分析结果是后续总体设计与详细设计的基础。

## 第4章 系统总体设计

### 4.1 设计目标与原则

结合第3章的需求分析，系统的总体设计遵循以下原则：

（1）证据驱动原则。系统的所有分析结论必须建立在可核查的证据之上。为此，设计上需要区分三类证据来源并采用不同的访问方式：当前代码以代码工作区为权威来源，通过文件工具实时读取；缺陷、合并请求、持续集成等实时状态以数据库或平台接口为权威来源，通过结构化查询获取；历史文档、讨论与经验以检索增强生成为召回通道。这一"研发数据分流"策略避免了用过期文档解释当前代码、用历史讨论判断最新状态的问题。

（2）分层解耦原则。系统自下而上划分为数据基础、知识与工具、智能协作、应用服务与用户五个层次，层与层之间通过明确定义的接口交互。模型、编排、工具、存储各自独立演进，例如更换大语言模型不影响工具层，新增工具不影响前端。

（3）人机协同原则。系统定位为"助手"而非"替代者"：分析类能力以建议形式输出，需要人工核对；写操作类能力只生成草稿，人工确认后才执行。关键节点（工作流计划确认、记忆批准、草稿确认）均保留人工决策入口。

（4）安全可控原则。执行约束（最大步数、超时、重规划上限）、权限校验、审计日志在框架层统一实现，不依赖提示词的"自觉"；所有外部写操作默认关闭，显式启用。

（5）可观测与可评测原则。系统的每次运行都留下轨迹（工具调用、任务结果、指标），回答质量通过固定评测集持续度量，使系统改进有量化的依据。

### 4.2 总体架构设计

系统采用"Python 智能体后端 + Next.js 前端"的全栈架构，自下而上分为五层，总体架构如图4-1所示（图略，以文字描述代替）。

（1）数据基础层。负责数据的持久化与版本管理，包括：PostgreSQL 数据库（存储仓库、缺陷、合并请求、会话、运行记录等结构化数据）、Milvus 向量数据库（存储知识文档块的向量索引）、Git 工作区（保存仓库代码的本地检出，为代码读取与检索提供对应版本的代码快照）。

（2）知识与工具层。为智能体提供获取信息与执行动作的能力，包括：代码工作区工具（文件列举、读取与代码搜索）、平台接口工具（读取缺陷、合并请求、持续集成信息）、检索增强生成工具（知识检索）、记忆工具（会话与项目记忆的检索与写入）以及安全工具（风险分类）。工具层还通过模型上下文协议与技能运行时（Skill Runtime）支持外部能力接入与稳定流程的复用。

（3）智能协作层。系统的核心层，由对话智能体与多智能体工作流组成。对话智能体负责理解用户问题、选择工具、组织证据并生成回答；当问题涉及跨领域综合决策时，对话智能体将任务转交工作流：规划智能体拆解任务，调度器按依赖调度并执行任务，观察智能体检查证据与冲突，综合智能体汇总结论。

（4）应用服务层。由 FastAPI 应用构成，负责接收前端请求、校验参数、确定仓库与会话上下文（上下文组装器）、调用智能协作层执行、并通过 SSE 持续推送执行进度，最后保存会话记录与运行轨迹。

（5）用户层。由 Next.js 前端应用构成，用户在此选择仓库与会话、提交分析问题、查看流式执行进度与分析结果、管理知识库与评测任务。

一次典型请求在各层之间的流转过程为：用户在前端提交问题；请求进入应用服务层，上下文组装器组织仓库信息、历史对话、相关记忆与预检索证据；对话智能体判断需要的工具并执行调用，收集判断所需信息；若问题需要综合分析，则进入多智能体工作流完成分工分析与汇总；结果返回前端的同时，会话记录、工具调用与运行轨迹持久化到数据基础层，可复用的项目经验经确认后进入记忆体系供后续召回。

### 4.4 数据库设计

#### 4.4.1 设计思路

系统的数据存储遵循"结构化数据入关系库、语义向量入向量库、代码快照入工作区"的分工原则。PostgreSQL 作为事实源（Source of Truth），存储所有结构化与派生数据；Milvus 仅存储知识文档块的向量及其隔离字段，可通过来源标识回溯到关系库中的原始记录；代码则以 Git 检出形式保存在本地工作区，供实时读取。所有表使用 UUID 作为主键，外键统一指向仓库（repositories）或会话（conversations）实体，保证数据可按仓库维度隔离与级联清理。

| 会话记忆域 | thread_memories / conversation_memories | 项目级与会话级结构化记忆（事实、决策、待办、偏好、引用等） |
| 会话记忆域 | memory_candidates / recall_events | 候选记忆（待批准）与召回事件记录 |
| 运行轨迹域 | agent_runs | 对话智能体单次运行记录（用户消息、路由、工具调用、最终回答） |
| 运行轨迹域 | agent_workflow_runs / agent_task_runs | 工作流级与任务级运行记录（规格、观察、指标、状态） |
| 安全审计域 | action_drafts | 操作草稿（类型、目标、风险级别、状态、确认人、执行结果） |
| 安全审计域 | audit_logs | 审计日志（操作、目标、状态、请求与结果） |
| 评测域 | eval_runs | 评测运行记录（结果指标、逐题轨迹、诊断信息） |

以缺陷表与工作流任务表为例说明关键字段设计。缺陷表（issues）包含：仓库外键、平台缺陷编号、标题、正文、状态、标签（JSON）、作者、指派人与各时间戳字段，其中仓库外键与编号建立组合索引以支持按仓库快速查询。多智能体任务表（agent_task_runs）包含：所属工作流外键、任务标识、智能体名称、任务类型、输入快照（JSON）、结果（JSON）、状态、错误信息与起止时间；任务结果以 JSON 保存，兼容不同任务类型的异构输出，同时保留状态与错误列以支持按状态检索与统计。

#### 4.4.3 索引与隔离设计

为支撑常见查询模式，系统在仓库外键、平台编号、状态、时间等高频过滤字段上建立索引；会话与仓库删除时通过级联约束清理从属数据。知识文档表通过仓库标识与来源类型标签实现检索隔离：检索时强制附加仓库过滤条件，保证一个仓库的分析只能召回本仓库的知识，这一点在测试中通过专门的项目隔离用例进行验证。

### 4.5 接口设计

#### 4.5.1 接口总体风格

后端接口遵循 REST 风格，统一以 `/api` 为前缀，按资源划分为仓库（repos）、缺陷（issues）、合并请求（pull_requests）、持续集成（ci）、对话（chat）、知识检索（rag、knowledge）、报告（reports）、工作区（workspaces）、代码图（code_graph）、检索（search）、草稿（action_drafts）、评测（evaluations）、技能（skills）、反馈（feedback）、会话（conversations）、项目索引（project_index）与平台回调（webhooks）等分组。请求与响应体均为 JSON，并借助 Pydantic 模型进行结构校验。

#### 4.5.2 主要接口说明

系统主要接口分组如表4-3所示。

**表4-3 主要接口分组**

| 接口分组 | 代表性接口 | 功能说明 |
|---------|-----------|---------|
| repos | POST /api/repos、POST /api/repos/{id}/sync、GET /api/repos/{id}/sync-status | 仓库连接、手动同步与同步状态查询 |
| issues | GET /api/issues、POST /api/issues/{id}/analyze | 缺陷列表与缺陷智能分析 |
| pull_requests | GET /api/pull_requests、POST /api/pull_requests/{id}/review | 合并请求列表与风险审查 |
| ci | GET /api/ci/runs、POST /api/ci/runs/{id}/debug | 构建运行记录与失败排障 |
| chat | POST /api/chat（SSE 流式）、GET /api/chat/stream | 对话智能体入口，流式推送执行事件 |
| rag | POST /api/rag/{repo_id}/search、POST /api/rag/{repo_id}/ask、POST /api/rag/{repo_id}/reindex | 知识检索、问答与索引重建 |
| knowledge | POST /api/rag/knowledge-bases、POST /api/rag/knowledge-bases/{repo_id}/documents | 知识库创建与文档上传解析 |
| evaluations | POST /api/evals/rag/run、GET /api/evals/{eval_id} | 评测提交与结果轮询 |
| action_drafts | GET /api/action-drafts、POST /api/action-drafts/{id}/confirm | 草稿列表与人工确认执行 |
| reports | POST /api/reports/weekly | 工程周报生成 |

其中对话接口采用 SSE 协议返回流式事件：客户端建立连接后，服务端依次推送"规划开始、任务计划、工具调用开始与结束、任务执行进度、答案分片、运行结束"等事件，前端据此渲染执行轨迹与逐字输出；评测提交接口采用"立即返回并后台执行"的异步模式，客户端凭评测标识轮询进度，页面刷新或离开不会中断后台任务。

### 4.6 部署架构设计

系统采用容器化基础设施与本地应用进程相结合的部署方式。基础设施服务通过 Docker Compose 编排，包括：PostgreSQL 16（含 pgvector 扩展，容器端口映射至 5434）、etcd（Milvus 的元数据存储）、MinIO（Milvus 的对象存储）、Milvus 独立部署模式（向量检索服务）以及可选的 Redis 服务。应用侧，后端以 Uvicorn 进程运行于 8000 端口，前端以 Next.js 开发服务器或生产构建运行于 3000 端口。系统配置通过根目录环境变量文件统一管理，涵盖数据库连接、模型接入参数（模型名、接口地址、密钥）、嵌入与重排模型配置、检索参数、上下文预算参数、评测阈值与安全密钥等，部署时按环境覆盖即可。

该部署方式的优点是：基础设施复用官方镜像，版本与数据卷清晰可控；应用进程本地运行便于开发调试；通过环境变量区分开发与演示环境，例如演示环境可以关闭向量检索并启用确定性的本地嵌入与启发式重排，使页面与结构化数据在没有图形处理器或外部模型服务时也可验证，同时系统会将该状态明确标记为"降级"，避免与完整链路状态混淆。

### 4.7 本章小结

本章阐述了系统的总体设计。首先提出了证据驱动、分层解耦、人机协同、安全可控、可观测与可评测五项设计原则；然后给出了五层总体架构并描述了典型请求的流转过程；随后划分了八个功能模块，完成了数据库的域划分、核心表与索引隔离设计；接着设计了 REST 接口分组与 SSE 流式协议；最后说明了容器化基础设施与本地应用进程相结合的部署架构。本章设计为第5章的详细实现提供了框架性依据。
