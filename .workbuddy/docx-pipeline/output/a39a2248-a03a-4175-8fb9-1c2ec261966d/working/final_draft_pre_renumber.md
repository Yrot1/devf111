# 基于多智能体协作的研发协作系统设计与实现

## 摘要

在团队软件研发过程中，判断一次代码改动能否合入、定位一次持续集成失败的根因、评估一个缺陷的优先级，往往需要同时查阅代码变更、缺陷描述、评审评论、构建日志和项目文档。这些研发信息分散在代码仓库、项目管理平台、持续集成系统和团队知识库中，工程师需要先花费大量时间收集与整理上下文，才能进入真正的分析决策环节。大语言模型具备较强的语言理解与推理能力，但直接使用通用对话模型处理研发协作问题，仍存在证据来源不权威、上下文组织困难、复杂问题分析深度不足、涉及写操作时安全风险高等问题。

针对上述问题，本文设计并实现了一个面向研发协作场景的多智能体系统。系统采用 Python 智能体后端与 Next.js 前端的全栈架构，自下而上划分为数据基础层、知识与工具层、智能协作层、应用服务层和用户层五层结构。本文的主要工作包括：第一，构建研发数据接入与同步模块，实现代码仓库中缺陷、合并请求、持续集成运行记录、代码文件与评审评论等数据的同步、分页覆盖范围报告与状态管理；第二，设计基于原生工具调用机制的对话智能体，通过状态图组织"决策—工具执行—结果观察"循环，并实现最大步数、重复调用检测、工具错误分类处理等执行约束；第三，设计"规划—调度—观察—综合"多智能体工作流，由规划智能体拆解任务并声明依赖关系，调度器按依赖就绪情况并行执行任务，观察智能体检查证据缺口与结论冲突，综合智能体汇总形成统一建议，同时支持有限次数的重规划；第四，实现工程化的检索增强生成链路，包括文档结构感知切分、向量与关键词双路混合召回、加权融合、重排、编号引用、按仓库隔离检索与召回测试；第五，设计分层上下文预算与跨会话记忆机制、安全草稿与人工确认机制，以及基于 RAGAS 的回答质量评测与回归验证体系。此外，系统采用"研发数据分流"策略：当前代码通过工作区工具读取，实时状态通过数据库或接口查询，历史非结构化知识进入检索增强生成链路，避免将过期信息当作事实。

系统在本地容器化环境中完成部署，功能测试与集成测试覆盖数据同步、智能体循环、工作流编排、检索链路、上下文压缩、项目隔离与安全确认等关键链路；基于固定评测集与 RAGAS 指标的评测体系能够对回答质量进行量化，并支持同一基线的回归对比与失败诊断。结果表明，该设计能够为缺陷分诊、合并请求审查、持续集成排障与版本发布检查等场景提供带证据的分析建议，并以安全草稿方式承接外部写操作，为研发协作类智能体系统的工程设计提供了一种可行方案。

**关键词：** 大语言模型；智能体；多智能体协作；检索增强生成；研发协作

## Abstract

In team software development, deciding whether a code change can be merged, diagnosing the root cause of a CI failure, or evaluating the priority of an issue usually requires reviewing code changes, issue descriptions, review comments, build logs and project documents at the same time. Such information is scattered across code repositories, project management platforms, CI systems and team knowledge bases, so engineers must spend considerable time collecting and organizing context before reaching the analysis and decision stage. Large language models (LLMs) have strong language understanding and reasoning capabilities, but directly applying a general-purpose chat model to development collaboration tasks still suffers from unauthoritative evidence, difficult context organization, insufficient depth for complex problems, and security risks in write operations.

To address these problems, this thesis designs and implements a multi-agent system for development collaboration scenarios. The system adopts a full-stack architecture with a Python agent backend and a Next.js frontend, and is organized into five layers: the data foundation layer, the knowledge and tool layer, the intelligent collaboration layer, the application service layer and the user layer. The main work of this thesis includes: first, a repository data ingestion and synchronization module that synchronizes issues, pull requests, CI runs, code files and review comments with pagination coverage reporting and status management; second, a conversational agent based on native tool calling, whose "decision–execution–observation" loop is organized as a state graph with execution constraints such as a maximum step limit, repeated-call detection and categorized tool error handling; third, a "plan–orchestrate–observe–synthesize" multi-agent workflow, in which the planner decomposes tasks and declares dependencies, the orchestrator executes ready tasks in parallel, the observer inspects evidence gaps and conflicting conclusions, and the synthesizer produces a unified recommendation, with bounded replanning; fourth, an engineered Retrieval-Augmented Generation (RAG) pipeline featuring structure-aware chunking, hybrid retrieval combining dense vectors and keyword search, weighted fusion, reranking, numbered citations, per-repository isolation and retrieval testing; fifth, a layered context budget and cross-session memory mechanism, a safety draft mechanism with human confirmation, and a RAGAS-based answer quality evaluation and regression verification system. In addition, the system adopts a "development data triage" strategy: current code is read through workspace tools, real-time status is queried from the database or APIs, and historical unstructured knowledge enters the RAG pipeline, avoiding treating outdated information as facts.

The system is deployed in a local containerized environment. Functional and integration tests cover key paths such as data synchronization, the agent loop, workflow orchestration, the retrieval pipeline, context compression, project isolation and safety confirmation. The evaluation system based on a fixed test suite and RAGAS metrics can quantify answer quality and support regression comparison and failure diagnosis against the same baseline. The results show that the design can provide evidence-backed analysis suggestions for issue triage, pull request review, CI debugging and release readiness checking, and can carry out external write operations through safety drafts, offering a feasible engineering approach for development collaboration agent systems.

**Key words:** large language model; agent; multi-agent collaboration; retrieval-augmented generation; development collaboration

## 第1章 绪论

### 1.1 研究背景与意义

随着软件系统规模不断扩大与团队协作方式持续演进，软件研发活动已经高度平台化、分布式化。一个中等规模的研发团队，日常需要同时维护代码仓库、缺陷跟踪系统、合并请求（Pull Request，PR）评审流程、持续集成（Continuous Integration，CI）流水线和团队知识库等多个平台。研发协作中大量高频问题的答案并非来自单一数据源，而是需要跨平台交叉验证。例如，判断一次代码改动能否合入，需要先确认合并请求改写的内容，再查阅关联缺陷中的需求背景、评审者留下的讨论意见以及自动化检查的运行结果；排查一次构建失败，需要从失败任务日志中提取关键错误，再结合当前代码状态与历史文档判断原因。这些信息分散且数量庞大，仅"找齐背景与证据"这一步就会消耗工程师大量时间，对不熟悉项目的新成员而言尤其困难。

大语言模型（Large Language Model，LLM）的出现为解决上述问题提供了新的技术路径。以 Transformer 架构为基础的预训练语言模型经过大规模语料训练与指令微调后，具备了强大的自然语言理解、生成与推理能力，能够胜任摘要、分类、问答等多种任务。然而，在研发协作这一专业场景中，直接使用通用对话模型存在明显不足：其一，模型的参数化知识无法覆盖特定项目的最新代码与实时状态，容易产生与事实不符的"幻觉"；其二，研发问题往往涉及多源证据的收集与比对，单轮问答难以完成系统性的信息整合；其三，简单地堆砌对话历史会迅速耗尽模型的上下文窗口，影响长会话的可用性；其四，模型若被赋予直接操作外部系统的能力，误操作可能对真实仓库造成不可逆的影响。

智能体（Agent）范式的提出为解决这些不足提供了新的思路。智能体将大语言模型从"文本生成器"升级为"任务执行者"：模型通过工具调用（Tool Calling）与外部世界交互，通过"推理—行动—观察"的循环逐步收集证据、修正判断，最终完成任务。当任务复杂度进一步提高、需要跨领域综合分析时，单智能体又面临职责边界模糊、分析深度不足的问题，多智能体协作（Multi-Agent Collaboration）随之成为研究与工程实践的热点——由多个职责明确的专用智能体分工完成子任务，再由更高层的规划与汇总机制形成整体结论。

本文正是在上述背景下开展研究与设计的。本文设计并实现了一个面向研发协作场景的多智能体系统，它连接代码仓库数据，能够分析缺陷、审查合并请求、排查持续集成失败、检索项目知识，并在多智能体协作模式下回答"版本能否发布"这类跨领域工程决策问题。本课题的研究意义体现在两个方面。在工程实践层面，系统完整覆盖了数据接入、知识检索、智能体协作、安全执行与效果评测五个环节，探索了大语言模型应用从"演示可用"走向"工程可靠"所需的关键设计，包括证据溯源、执行约束、人机协同与量化评测等。在技术学习层面，本文对智能体循环、检索增强生成、多智能体任务调度、上下文管理、安全草稿与评测工程等当前大模型应用领域的前沿课题进行了系统性的梳理与实现验证，对理解新一代 AI 应用架构具有参考价值。

### 1.2 国内外研究现状

#### 1.2.1 大语言模型与智能体技术

智能体技术的核心是让语言模型具备与外部环境交互的能力。Yao 等人提出的 ReAct 范式[5]将推理（Reasoning）与行动（Acting）交织进行，模型在每一步先生成思考轨迹，再决定调用何种工具并观察返回结果，从而在知识密集型任务中显著优于只做推理或只做行动的方法。Schick 等人提出的 Toolformer[6]进一步验证了语言模型可以通过自监督方式学会在合适的位置调用外部工具接口。Mialon 等人对增强语言模型进行了系统综述[19]，将"推理、工具、记忆"归纳为语言模型增强的三条主线。在工程实践层面，基于原生工具调用的智能体框架（如 LangChain[21]与 LangGraph[22]）被广泛采用，前者统一了模型、工具与消息的抽象，后者以状态图（State Graph）方式显式建模智能体的执行流程、分支与停止条件，使多轮工具调用具备可控的执行边界。

#### 1.2.2 检索增强生成技术

检索增强生成（Retrieval-Augmented Generation，RAG）由 Lewis 等人系统提出[7]，其核心思想是在生成回答前先检索外部知识，将检索到的证据与问题一同交给模型，从而缓解幻觉并提升回答的可溯源性与时效性。检索环节的技术演进经历了从稀疏检索到稠密检索、再到混合检索的过程：BM25 作为经典的稀疏检索算法，基于词项频率与文档长度归一化计算相关性[9]；Karpukhin 等人提出的稠密段落检索（DPR）[8]使用双塔结构将问题与文档映射到同一向量空间，通过语义相似度召回候选。Cormack 等人提出的倒数排名融合（Reciprocal Rank Fusion，RRF）[11]为不同召回路径的结果融合提供了简单而有效的方法。在召回之后，Nogueira 等人采用交叉编码器对候选段落进行重排[10]，进一步提升排序质量。Gao 等人的综述[13]将 RAG 的发展归纳为朴素 RAG、高级 RAG 与模块化 RAG 三个阶段，并指出工程化 RAG 系统需要在切分策略、检索策略、重排与评测等环节进行系统设计。评测方面，Es 等人提出的 RAGAS 框架[12]从上下文精确率、上下文召回率、答案忠实度与答案相关性等维度对 RAG 系统进行自动化评估，已成为该领域被广泛采用的评测工具。

#### 1.2.3 多智能体协作技术

多智能体协作将复杂任务拆解给多个职责明确的智能体。Park 等人提出的生成式智能体[14]通过记忆、反思与规划机制的组合，让多个智能体在开放环境中产生可信的协作行为，验证了多智能体架构在复杂任务中的潜力。Wu 等人提出的 AutoGen[15]以"可对话智能体"为核心抽象，支持多智能体通过对话协同完成代码生成与执行等任务，并允许人类以参与者身份介入。面向软件开发场景，Hong 等人提出的 MetaGPT[16]与 Qian 等人提出的 ChatDev[17]将软件公司中的角色分工（产品经理、架构师、程序员、测试员等）映射为智能体角色，通过标准化的中间产物（如需求文档、设计文档）在角色之间传递信息，展示了多智能体在软件工程流程中的可行性。总体来看，现有多智能体研究多聚焦于任务生成与流程模拟，而面向真实研发数据（仓库代码、缺陷、合并请求、构建日志）的协作分析系统，以及配套的证据校验、冲突检查与安全控制机制，仍存在较大的工程探索空间。

#### 1.2.4 现有研发协作工具的不足

当前研发协作领域已有若干工具化实践：代码托管平台内置了静态检查与自动评审能力，集成开发环境中的编程助手可以补全代码、解释片段。但这类工具多聚焦于"代码本身"，对研发协作中"跨平台信息收集与判断"这一关键环节的支持仍然有限：缺陷、评审讨论、构建日志与项目文档之间的关联关系没有被有效利用；分析结论往往缺少可核查的证据链；面对"该不该合入""该不该发布"这类需要综合多源信息的决策问题，缺乏系统性的多智能体分工协作机制；此外，赋予工具自动执行写操作的能力时，缺乏草稿确认、权限校验与审计留痕等安全设计。上述不足正是本文工作试图填补的空间——面向研发协作场景，构建一个证据驱动、人机协同、安全可控的多智能体分析系统。

### 1.3 主要研究内容

围绕上述目标，本文的主要研究内容包括以下五个方面：

（1）研发数据接入与同步。设计并实现代码仓库数据的连接、分页同步与状态管理机制，将分散在代码托管平台各处的缺陷、合并请求、变更文件、评审评论、持续集成运行记录与日志等数据统一落库，并设计同步覆盖范围的报告机制与仓库健康检查，为后续分析提供可靠的数据底座。

（2）对话智能体与工具调用循环。基于原生工具调用机制设计对话智能体，通过状态图组织"决策—工具执行—结果观察"的多轮循环；设计工具注册与结构化参数校验、最大步数与重复调用限制、工具错误分类与重试等执行约束，保证智能体在可控边界内完成任务。

（3）多智能体协作工作流。设计"规划—调度—观察—综合"四角色协作架构：规划智能体负责任务拆解、依赖声明与验收标准定义；调度器按任务依赖就绪情况并行调度并处理失败跳过；观察智能体负责合并门禁检查、跨智能体结论冲突检测与证据缺口识别；综合智能体负责汇总形成统一建议；同时设计有限重规划机制，避免工作流陷入无效循环。

（4）工程化检索增强生成链路。设计研发数据分流策略与文档处理流水线，实现结构感知切分、向量与关键词混合召回、加权融合、重排、编号引用、按仓库隔离与召回测试，并处理"证据不足时拒答"的答案门禁问题。

（5）上下文管理、安全执行与效果评测。设计分层上下文预算与压缩机制、跨会话记忆的沉淀与人工批准机制、写操作的安全草稿与审计机制，以及基于固定评测集与 RAGAS 指标的量化评测与回归对比体系。

## 第2章 相关技术基础

### 2.1 大语言模型与提示工程

#### 2.1.1 大语言模型基本原理

本文所依托的大语言模型以 Transformer 架构[1]为基础。Transformer 抛弃了循环神经网络（Recurrent Neural Network，RNN）的序列递推结构，完全基于自注意力机制（Self-Attention）建模序列中任意两个位置之间的依赖关系，具备良好的并行训练能力与长距离依赖建模能力。其核心计算如式（2-1）所示：

Attention(Q, K, V) = softmax(QKᵀ / √d_k)V　　（2-1）

其中 Q、K、V 分别表示查询矩阵、键矩阵与值矩阵，d_k 为键向量的维度。多头注意力机制将上述计算在多个子空间中并行执行再拼接，使模型能够从不同表示子空间捕捉语义信息。

大语言模型的训练通常分为两个阶段：第一阶段为预训练，模型在海量文本上以自回归方式学习下一个词的预测，获得通用的语言能力与世界知识[2]；第二阶段为指令微调与基于人类反馈的强化学习（Reinforcement Learning from Human Feedback，RLHF）[3]，通过人工标注的指令数据与偏好数据对模型进行对齐，使其输出更符合人类指令意图。经过两个阶段训练后的模型具备零样本与少样本学习能力，能够按照自然语言指令完成分类、摘要、抽取、推理等多种任务，这是构建智能体系统的能力基础。

#### 2.1.2 提示工程与结构化输出

提示工程（Prompt Engineering）指通过精心设计输入提示来引导模型产生期望输出的方法。Wei 等人提出的思维链（Chain-of-Thought）提示[4]表明，在提示中引导模型先给出推理过程再给出结论，可以显著提升模型在数学与逻辑推理任务上的表现，这一思想后续被广泛吸收进智能体的推理循环设计中。

在工程系统中，模型输出不仅是给人阅读的文本，还需要被程序消费。本文系统采用结构化输出（Structured Output）方案：通过 Pydantic 模型定义输出 Schema，要求模型以 JSON 格式返回分析结果，并在运行时对返回内容进行类型校验与约束检查。相比自由文本，结构化输出使分析结果可直接入库、渲染与二次加工，同时当模型输出不符合 Schema 时可以触发重试或降级，提高了系统的鲁棒性。

### 2.2 工具调用与智能体循环

工具调用（Tool Calling）是模型与外部系统交互的标准化接口。系统在请求中向模型声明一组可用工具及其参数 Schema，模型根据当前任务决定是否调用工具、调用哪个工具以及传入什么参数；系统执行工具后将结果回传给模型，模型继续决定下一步动作，直至任务完成或触发停止条件。

这一"决策—执行—观察"的循环被称为智能体循环（Agent Loop），其概念源头可追溯到 ReAct 范式[5]。一个健壮的 Agent Loop 需要解决以下工程问题：第一，循环停止条件，包括任务完成、达到最大步数上限、重复调用检测等，防止无界循环；第二，工具错误处理，工具可能因网络、权限、数据缺失等原因失败，系统需要对错误分类并决定重试、降级或终止；第三，观测结果的组织，工具返回结果可能非常长，需要截断、摘要或结构化压缩后再回传给模型；第四，安全性，敏感工具（如写操作）需要权限校验与人工确认。本文第5章介绍的对话智能体正是围绕上述问题展开设计的。

### 2.3 LangChain 与 LangGraph 编排框架

LangChain[21]是当前应用最广泛的大语言模型应用开发框架之一，它提供了模型（Chat Model）、消息（Message）、工具（Tool）等核心抽象，统一了不同模型厂商接口的调用方式，并将工具的参数校验、调用执行封装为可复用的组件。本文系统的对话智能体基于 LangChain 的工具抽象注册工具集，通过 OpenAI 兼容接口接入大语言模型服务。

LangGraph[22]在 LangChain 基础上进一步提供基于状态图（State Graph）的编排能力。开发者将智能体的执行过程建模为若干节点（Node）与边（Edge）：节点表示一个计算步骤（如模型决策、工具执行），边表示步骤之间的流转条件。相较于线性链式调用，状态图的优势在于：流程分支与循环显式可查；执行状态（消息、中间结果、计数器等）统一管理；支持中断、恢复与可视化。本文系统的对话智能体以状态图组织执行循环，将"模型推理""工具执行"等步骤定义为节点，并根据模型是否产生工具调用决定下一步流向，使多轮循环的停止条件具备显式、可控的结构。

### 2.4 检索增强生成

检索增强生成（RAG）由 Lewis 等人提出[7]，其基本流程可概括为三个阶段：

（1）索引阶段。将外部知识文档进行解析与切分，得到若干文本块（Chunk），通过嵌入模型将文本块映射为语义向量并存入向量数据库，同时对文档块附加来源、时间等元数据。

（2）检索阶段。将用户问题同样映射为向量，在向量数据库中检索语义相近的文本块；为提高召回质量，工程系统通常同时执行关键词检索，并对多路结果进行融合与重排。

（3）生成阶段。将检索到的证据片段与用户问题一同组织进提示词，引导模型"基于给定证据"生成回答，并在回答中标注引用来源。

RAG 在本文系统中的定位是"历史与非结构化知识的语义召回通道"，与工作区代码检索、数据库结构化查询共同构成三类证据来源，其详细设计见第5.4节。

### 2.5 混合检索与重排技术

单一检索路径存在固有局限：稀疏检索（如 BM25）依赖词项匹配，擅长捕获专有名词、错误码等精确匹配信号，但无法理解语义改写；稠密检索基于语义向量，擅长同义表达与模糊语义，但对罕见词的区分度较低。工程实践因此普遍采用混合检索（Hybrid Retrieval）。

BM25 评分函数如式（2-2）所示：

Score(q, d) = Σ IDF(q_i) · (f(q_i, d) · (k₁ + 1)) / (f(q_i, d) + k₁ · (1 − b + b · |d| / avgdl))　　（2-2）

其中 f(q_i, d) 为词项 q_i 在文档 d 中的出现频次，|d| 为文档长度，avgdl 为平均文档长度，k₁ 与 b 为可调参数，分别控制词频饱和程度与长度归一化强度[9]。

多路召回结果的融合方法中，倒数排名融合（RRF）[11]仅依赖各路的排名位置而非原始分数，避免了不同打分体系不可比的问题，其公式如式（2-3）所示：

RRF(d) = Σ 1 / (k + rank_i(d))　　（2-3）

其中 rank_i(d) 为文档 d 在第 i 路召回中的排名，k 为平滑常数。在本文系统的实现中，考虑到两类召回分数的可比性，融合环节同时引入了带权重的分数融合与双路命中奖励策略（详见第5.4.4节）。

重排（Rerank）阶段使用交叉编码器（Cross-Encoder）模型对候选段落与问题做联合编码打分[10]。与双塔结构中问题与文档独立编码不同，交叉编码器能够建模问题与文档之间的细粒度交互，排序精度更高，但计算开销大，因此通常只对召回阶段的 Top-N 候选（如几十条）进行重排，从中筛选最终的 Top-K 证据。

### 2.6 系统开发与部署技术

本文系统的后端采用 Python 语言，Web 框架为 FastAPI，其基于类型注解的依赖注入与 Pydantic 数据校验模型能够显著降低接口层与模型层的开发成本；数据访问层使用 SQLAlchemy ORM，数据库为 PostgreSQL 16（配合 pgvector 扩展）。向量检索使用 Milvus 分布式向量数据库[18]，其支持亿级向量的相似性检索，并通过分区与标量过滤满足多租户隔离需求。前后端之间的实时进度推送采用服务器发送事件（Server-Sent Events，SSE）协议，相比轮询具备更低的延迟与更小的服务端开销。

前端采用 Next.js 15 与 React 19 框架，使用 TypeScript 作为开发语言，样式方案为 Tailwind CSS，数据获取与缓存采用 TanStack React Query，并配合 React Markdown 渲染模型输出的富文本内容。整个系统通过 Docker Compose 编排部署，将 PostgreSQL、Milvus、etcd、MinIO 等基础服务容器化，后端与前端以本地进程方式运行，配置项通过环境变量文件统一管理。

### 2.7 本章小结

本章介绍了本文所涉及的关键技术基础，包括大语言模型与提示工程的基本原理、工具调用与智能体循环的工作机制、LangChain 与 LangGraph 编排框架的设计思想、检索增强生成的流程、混合检索与重排算法的技术要点，以及系统开发与部署所用的主流技术栈。上述技术构成了后续章节系统设计与实现的技术依据。
## 第3章 系统需求分析

### 3.1 系统设计目标与可行性分析

#### 3.1.1 系统设计目标

本系统的总体目标是：面向软件研发协作场景，构建一个能够连接代码仓库数据、理解研发上下文、提供带证据分析建议的智能协作系统。具体目标包括：

（1）数据连通性。打通代码仓库中缺陷、合并请求、持续集成、代码与文档等多源数据，建立统一的本地数据底座，使分析活动不再依赖人工跨平台收集信息。

（2）分析专业性。针对缺陷分诊、合并请求审查、持续集成排障三类高频任务，分别设计专用的分析智能体，输出分类、优先级、风险点、修复建议等结构化结论，而非笼统的问答回复。

（3）协作系统性。对"版本能否发布"这类需要跨领域综合的问题，提供多智能体协作机制，由规划、执行、观察、综合等角色分工完成分析，并显式处理证据缺口与结论冲突。

（4）证据可溯源。所有分析结论必须附带证据来源（代码位置、缺陷编号、日志片段、文档引用），检索范围按仓库隔离，检索不到证据时如实说明而不是编造。

（5）执行安全性。系统对涉及外部系统写操作（如提交评论、创建缺陷）的能力采用"草稿—人工确认—执行—审计"的安全流程，保证智能体具备执行能力但不越权。

（6）效果可度量。建立固定评测集与量化指标体系，回答质量可测量、改动效果可回归对比，为系统持续迭代提供依据。

#### 3.1.2 可行性分析

技术可行性方面，系统所依赖的大语言模型经 OpenAI 兼容接口接入，可灵活切换；后端 FastAPI、数据层 PostgreSQL 与 Milvus、编排框架 LangChain 与 LangGraph、前端 Next.js 等技术均有成熟的社区生态与文档支持；工具调用、SSE 推送、结构化输出等关键机制均有标准的实现范式，技术风险可控。

经济可行性方面，系统全部基于开源组件构建，基础服务均可通过 Docker 在单机环境部署；大语言模型与嵌入模型的调用成本与使用量成正比，在开发与中小团队使用规模下成本较低；系统不依赖专有商业组件，具备良好的经济性。

操作可行性方面，系统以 Web 应用形式呈现，提供仓库管理、对话、分析结果、评测等图形化页面，研发人员无需了解内部实现即可使用；同步、分析、评测等操作均可在页面一键触发，交互成本低。

### 3.2 功能需求分析

根据研发协作的实际场景，系统功能需求可归纳为以下十一项，如表3-1所示。

**表3-1 系统功能需求汇总**

| 编号 | 功能名称 | 功能描述 |
|------|---------|---------|

下面对核心功能需求做进一步说明。

（1）仓库接入与数据同步（FR1）。系统需要支持用户填写仓库地址与访问凭据完成仓库接入，并按分页方式从代码托管平台同步数据。考虑到大仓库全量同步耗时较长，首次接入应支持仅取少量记录进行快速体验；正式同步与定时同步则默认读取全部分页，并允许设置每类记录的总数上限。同步完成后需要向用户报告实际覆盖范围，状态需区分"完整完成""请求成功但为空""达到数量上限或部分失败""全部失败"与"未选择数据源"五种情形；部分失败时应保留已有明细数据，不更新最近成功同步时间，避免将不完整数据误认为完整快照。

（2）缺陷智能分诊（FR3）。输入为缺陷标题与描述（以及关联的历史证据），输出包括：缺陷类型分类（如功能缺陷、性能问题、文档问题等）、优先级建议、复杂度评估、负责人推荐、可执行的行动项列表以及可能的重复缺陷候选。输出采用结构化 Schema，保证可以被页面稳定渲染。

（3）合并请求风险审查（FR4）。输入为合并请求的变更文件与补丁内容，结合关联缺陷与历史评审讨论，输出变更摘要、关键变更说明、风险点列表（包括安全、鉴权、数据一致性等高风险路径的识别）、审查检查清单、测试建议以及"建议合入/暂缓合入"的决策建议。

（4）多智能体协同决策（FR6）。以"检查当前缺陷、合并请求与失败的持续集成，判断该版本是否可以发布"为典型用例：系统首先由规划智能体生成执行计划（包含任务清单、任务依赖与验收标准），用户确认后由调度器按依赖关系并行执行各分析任务（仓库状态检查、缺陷检查、合并请求检查、持续集成检查等），随后观察智能体检查各任务输出中的证据缺口、结论冲突与需人工确认事项，最后由综合智能体汇总形成统一结论。工作流执行过程与各智能体的输出需要完整记录并可在页面回看。

（5）知识检索与问答（FR7）。系统需要提供知识库管理（创建、上传文档、解析与索引）与检索问答能力。检索需要支持向量与关键词双路召回、融合排序、重排与分数阈值过滤；回答需要附带编号引用，明确标注证据出处；当检索不到足够证据时，系统应如实提示而不是给出无依据的回答。此外，提供召回测试能力，输入查询语句可直接查看各候选块的得分与排序，用于诊断切分与检索配置问题。

（6）安全草稿（FR10）。对涉及外部系统写操作的能力（如对合并请求发表评论、创建缺陷、添加标签），系统不允许模型直接执行，而是先生成操作草稿，包含操作类型、目标对象、拟执行的正文内容与风险级别；草稿经人工确认后方可执行，执行结果与失败原因写入审计日志。

### 3.3 非功能需求分析

（1）安全性需求。访问凭据（如代码托管平台令牌）仅通过环境变量或用户输入提供，持久化时必须加密存储，日志中不得打印令牌明文；写操作必须经过草稿与人工确认流程；系统需记录关键操作的审计日志；检索与问答必须按仓库隔离，防止跨仓库数据泄露。

（2）性能需求。同步接口需支持分页与数量上限控制，避免大仓库同步阻塞服务；对话链路的模型推理耗时较长，需通过流式推送保证用户可感知的响应性；多智能体工作流需为单任务设置超时上限（本系统取 90 秒），避免个别任务挂起拖垮整个工作流；上下文需要设置 token 预算（本系统默认输入上限为 24000 tokens），保证长会话不超过模型窗口。

（3）可观测性需求。每次对话需记录工具调用序列、引用来源与最终回答；多智能体工作流需持久化工作流级与任务级运行记录（含耗时、成功/失败/跳过统计、重规划次数等指标）；关键链路需输出结构化日志，便于定位"工具参数错误、检索证据不足、任务结论冲突"等典型问题。

（4）可扩展性需求。系统需提供标准化的工具扩展机制，支持通过模型上下文协议（Model Context Protocol，MCP）接入外部工具服务；支持将稳定的操作流程沉淀为技能（Skill）并在任务中按需激活；多智能体工作流的任务类型应可注册扩展，新增分析能力时无需改动调度框架。

（5）可用性需求。前端页面需覆盖仓库管理、对话、分析结果、评测等主要功能；长耗时操作需展示执行进度（规划、工具调用、任务进度）；错误信息需以用户可理解的方式呈现，并给出恢复建议。

## 第4章 系统总体设计

### 4.1 设计目标与原则

结合第3章的需求分析，系统的总体设计遵循以下原则：

（1）证据驱动原则。系统的所有分析结论必须建立在可核查的证据之上。为此，设计上需要区分三类证据来源并采用不同的访问方式：当前代码以代码工作区为权威来源，通过文件工具实时读取；缺陷、合并请求、持续集成等实时状态以数据库或平台接口为权威来源，通过结构化查询获取；历史文档、讨论与经验以检索增强生成为召回通道。这一"研发数据分流"策略避免了用过期文档解释当前代码、用历史讨论判断最新状态的问题。

（2）分层解耦原则。系统自下而上划分为数据基础、知识与工具、智能协作、应用服务与用户五个层次，层与层之间通过明确定义的接口交互。模型、编排、工具、存储各自独立演进，例如更换大语言模型不影响工具层，新增工具不影响前端。

（3）人机协同原则。系统定位为"助手"而非"替代者"：分析类能力以建议形式输出，需要人工核对；写操作类能力只生成草稿，人工确认后才执行。关键节点（工作流计划确认、记忆批准、草稿确认）均保留人工决策入口。

（4）安全可控原则。执行约束（最大步数、超时、重规划上限）、权限校验、审计日志在框架层统一实现，不依赖提示词的"自觉"；所有外部写操作默认关闭，显式启用。

（5）可观测与可评测原则。系统的每次运行都留下轨迹（工具调用、任务结果、指标），回答质量通过固定评测集持续度量，使系统改进有量化的依据。

### 4.2 总体架构设计

系统采用"Python 智能体后端 + Next.js 前端"的全栈架构，自下而上分为五层，总体架构如图4-1所示（图略，以文字描述代替）。

（1）数据基础层。负责数据的持久化与版本管理，包括：PostgreSQL 数据库（存储仓库、缺陷、合并请求、会话、运行记录等结构化数据）、Milvus 向量数据库（存储知识文档块的向量索引）、Git 工作区（保存仓库代码的本地检出，为代码读取与检索提供对应版本的代码快照）。

（2）知识与工具层。为智能体提供获取信息与执行动作的能力，包括：代码工作区工具（文件列举、读取与代码搜索）、平台接口工具（读取缺陷、合并请求、持续集成信息）、检索增强生成工具（知识检索）、记忆工具（会话与项目记忆的检索与写入）以及安全工具（风险分类）。工具层还通过模型上下文协议与技能运行时（Skill Runtime）支持外部能力接入与稳定流程的复用。

（3）智能协作层。系统的核心层，由对话智能体与多智能体工作流组成。对话智能体负责理解用户问题、选择工具、组织证据并生成回答；当问题涉及跨领域综合决策时，对话智能体将任务转交工作流：规划智能体拆解任务，调度器按依赖调度并执行任务，观察智能体检查证据与冲突，综合智能体汇总结论。

（4）应用服务层。由 FastAPI 应用构成，负责接收前端请求、校验参数、确定仓库与会话上下文（上下文组装器）、调用智能协作层执行、并通过 SSE 持续推送执行进度，最后保存会话记录与运行轨迹。

（5）用户层。由 Next.js 前端应用构成，用户在此选择仓库与会话、提交分析问题、查看流式执行进度与分析结果、管理知识库与评测任务。

一次典型请求在各层之间的流转过程为：用户在前端提交问题；请求进入应用服务层，上下文组装器组织仓库信息、历史对话、相关记忆与预检索证据；对话智能体判断需要的工具并执行调用，收集判断所需信息；若问题需要综合分析，则进入多智能体工作流完成分工分析与汇总；结果返回前端的同时，会话记录、工具调用与运行轨迹持久化到数据基础层，可复用的项目经验经确认后进入记忆体系供后续召回。

### 4.4 数据库设计

#### 4.4.1 设计思路

系统的数据存储遵循"结构化数据入关系库、语义向量入向量库、代码快照入工作区"的分工原则。PostgreSQL 作为事实源（Source of Truth），存储所有结构化与派生数据；Milvus 仅存储知识文档块的向量及其隔离字段，可通过来源标识回溯到关系库中的原始记录；代码则以 Git 检出形式保存在本地工作区，供实时读取。所有表使用 UUID 作为主键，外键统一指向仓库（repositories）或会话（conversations）实体，保证数据可按仓库维度隔离与级联清理。

### 4.6 部署架构设计

系统采用容器化基础设施与本地应用进程相结合的部署方式。基础设施服务通过 Docker Compose 编排，包括：PostgreSQL 16（含 pgvector 扩展，容器端口映射至 5434）、etcd（Milvus 的元数据存储）、MinIO（Milvus 的对象存储）、Milvus 独立部署模式（向量检索服务）以及可选的 Redis 服务。应用侧，后端以 Uvicorn 进程运行于 8000 端口，前端以 Next.js 开发服务器或生产构建运行于 3000 端口。系统配置通过根目录环境变量文件统一管理，涵盖数据库连接、模型接入参数（模型名、接口地址、密钥）、嵌入与重排模型配置、检索参数、上下文预算参数、评测阈值与安全密钥等，部署时按环境覆盖即可。

该部署方式的优点是：基础设施复用官方镜像，版本与数据卷清晰可控；应用进程本地运行便于开发调试；通过环境变量区分开发与演示环境，例如演示环境可以关闭向量检索并启用确定性的本地嵌入与启发式重排，使页面与结构化数据在没有图形处理器或外部模型服务时也可验证，同时系统会将该状态明确标记为"降级"，避免与完整链路状态混淆。

## 第5章 系统详细设计与实现

本章按照模块划分，依次介绍研发数据同步、对话智能体、多智能体工作流、检索增强生成、上下文与记忆、安全草稿、流式推送与运行轨迹、能力扩展以及前端交互的详细设计与实现。

### 5.1 研发数据接入与同步模块

#### 5.1.1 仓库管理设计

仓库是系统中所有数据的组织边界。仓库实体记录了代码托管平台类型、完整名称、克隆地址、本地检出路径与检出模式等信息。系统支持两种检出模式："托管模式"下由系统管理仓库代码的本地副本，配合工作区管理器在后台完成拉取与版本更新；"本地模式"下直接指向用户机器上已有的代码目录，避免重复占用磁盘。仓库记录还保存最近同步时间与同步元数据（JSON），元数据中记录了每类数据源的覆盖范围，为仓库健康检查提供依据。

#### 5.1.2 同步流程设计

数据同步的总体流程为：接收同步请求并解析参数（数据源选择与数量上限）→ 依次调用平台接口按分页拉取各类数据 → 逐类落库（新增或更新）→ 生成同步报告 → 更新同步元数据与最近成功同步时间。同步覆盖五类主数据：缺陷、合并请求（含变更文件列表）、评审评论、持续集成运行记录（含任务与步骤明细）以及失败运行的日志文本。

在数量控制方面，同步接口的 limit 参数表示"每类主记录的总数上限"：省略或传空表示读取全部分页；达到上限且存在后续记录时，报告中将该来源标记为"部分覆盖"。首次接入仓库时默认只取少量记录以快速完成体验；定时自动同步默认读取全部分页，也可通过环境变量设置总数上限。所有同步操作都会在响应中报告实际覆盖范围，供用户判断数据是否完整。

同步状态机设计为五种状态：completed（所选数据源完整完成）、empty（请求成功但数据为空）、partial（达到数量上限或部分来源失败）、failed（所选主接口全部失败）与 skipped（未选择该数据源）。状态判定的关键设计是"部分失败保留已有明细"：某一数据源失败时，不影响其他数据源已写入的数据，且不更新最近成功同步时间，使后续的健康检查能够识别数据陈旧风险。

自动同步由后台调度器实现：调度器按配置的间隔（默认 300 秒）扫描需要同步的仓库，调用同一套同步服务完成数据更新，从而保证系统在日常使用中数据始终接近最新状态。

#### 5.1.3 仓库健康检查

健康检查模块对仓库数据执行三项校验：数据是否为空、同步是否完整（是否存在 partial/failed 状态的数据源）、数据是否在时效窗口内（最近成功同步时间是否超过 24 小时）。三项校验的结果与统计数据共同构成仓库健康摘要。这一摘要不仅是独立的展示功能，还作为证据质量的判断依据之一：当多智能体工作流执行分析时，若健康检查发现数据不足或陈旧，观察智能体会阻止基于该数据给出"可推进"的结论，并要求先完成同步。这一设计体现了系统"不基于不完整证据下结论"的原则。

### 5.2 对话智能体与工具调用循环

#### 5.2.1 智能体总体设计

对话智能体（ChatAgent）是系统的统一入口。它接收用户消息与运行上下文，使用原生工具调用机制选择下一步动作，接收工具结果后继续判断，直至生成最终回答或触发停止条件。其工具集共十四项，按功能可分为五类：

（1）证据与记忆类：研发证据检索（devflow_search_evidence）、项目线程记忆读取（devflow_get_thread_context）与封存会话事件读取（devflow_read_session_events）；

（2）代码工作区类：文件列举、文件读取与代码搜索（workspace.list_files / read_file / search_code）；

（3）知识检索类：知识库相似文档检索（rag.search_similar_documents）；

（4）专用分析类：仓库健康摘要（repo_health.generate_summary）、缺陷分析（issue_agent.analyze_issue）、合并请求审查（pr_review_agent.analyze_pr）、构建排障（ci_debug_agent.analyze_workflow_run）、周报生成（report_agent.generate_weekly_report）与安全风险分类（safety_agent.classify_action_risk）；

（5）工作流入口：工程评审工作流（workflow.run_engineering_review），用于将跨领域综合问题转交多智能体工作流。

这一工具集设计体现了"简单问题直接查、专项问题专办、复杂问题协作办"的分层策略：一般性查询由智能体直接调用检索或工作区工具完成；明确属于缺陷、合并请求、构建排障的问题交由对应专用分析智能体；涉及跨领域决策的问题进入多智能体工作流。

#### 5.2.2 基于状态图的执行循环

执行循环以状态图实现，包含两类节点与若干条件边。状态对象载明消息、可用工具映射、观察结果列表、工具调用记录、引用、步骤计数、停止原因、模型用量与上下文统计等字段，随执行逐步累积。

每轮循环的主要步骤为：第一步，组装本轮提示，包括系统提示、压缩后的历史上下文、预检索证据与本轮用户消息；第二步，模型决策节点调用大语言模型，模型返回自然语言内容或工具调用请求；第三步，若模型请求工具调用，则进入工具执行节点：逐个校验参数结构、执行工具、收集结果并生成观察记录，随后沿条件边回到模型决策节点继续循环；若模型未请求工具调用，则视为任务完成，沿条件边流向结束节点，输出最终回答与引用。循环过程中产生的中间事件（决策、工具调用开始/结束、观察摘要）通过流式通道实时推送，并在运行结束后持久化。

#### 5.2.3 执行约束设计

为防止循环失控并提升鲁棒性，循环层实现了三重约束：

（1）步数上限。单次运行最多执行 12 步（max_steps = 12），达到上限时强制停止并基于已有观察生成收束性回答。

（2）重复调用限制。系统统计同一工具以相同参数被调用的次数，同一调用重复超过 2 次（max_repeated_tool_calls = 2）时判定为无效循环，终止运行并在回答中说明未能完成的原因，避免模型在证据不足时反复重试同一查询。

（3）工具错误分类与重试。工具执行错误被划分为八类：未知工具、超时、触发限流、瞬时网络故障、权限拒绝、数据不存在、模型输出非法与工具运行时错误。对瞬时性错误（超时、限流、网络故障）允许重试一次（tool_retry_attempts = 1）；对确定性错误（权限、数据不存在、参数非法）不重试，而是将错误信息作为观察结果回传模型，由模型调整策略或向用户说明。

在参数校验方面，工具调用参数通过结构化模型校验（兼容扩展字段的通用参数模型），非法参数在进入工具实现前即被拦截并转化为"模型输出非法"类错误，避免脏参数进入业务逻辑。模型调用侧设置温度参数为 0、超时 60 秒，并启用提示词缓存以降低重复系统提示的调用成本与延迟。

#### 5.2.4 上下文溢出恢复

长会话或大工具结果可能使请求超出模型上下文窗口。系统在两类时机进行防护：一是请求组装阶段的 token 预算裁剪（见第 5.5 节）；二是调用发生上下文溢出错误时，捕获该错误并执行一次"溢出恢复"流程——对历史与工具结果进行更激进的重压缩后重试，同时将恢复动作记入运行状态，保证恢复过程可观测、不无限重试。

### 5.3 多智能体协作工作流

#### 5.3.1 工作流总体设计

多智能体工作流用于处理"版本能否发布""合并请求能否合入"这类需要跨领域综合判断（Cross-domain Engineering Decision）的问题。工作流采用"规划—调度—观察—综合"四角色架构：

（1）规划智能体（PlannerAgent）。将用户目标拆解为边界明确的任务清单，生成工作流规格（WorkflowSpec）。规格中每个任务声明其标识、任务类型、所需输入与依赖关系（前置任务），并给出整体验收标准。规划智能体的提示词强调"任务粒度适中、依赖显式声明、验收标准可检查"。

（2）调度器（WorkflowOrchestrator）。负责执行任务图：反复扫描未完成任务，收集依赖已满足的任务并行执行，直至全部完成。调度器同时承担超时控制（单任务 90 秒）、失败处理与重规划驱动。

（3）观察智能体（ObserverAgent）。在所有可执行任务完成后，检查任务输出中的合并门禁（Merge Gate）条件、跨智能体结论冲突、低置信度结论、证据缺失与需要人工确认的事项，输出结构化观察报告；观察报告中每条发现均标注类型与涉及的任务。

（4）综合智能体（SynthesisAgent）。基于工作流规格、全部任务结果与观察报告，生成统一的决策备忘录，包含结论、依据、风险与建议的后续动作。

工作流的每一轮（Round）执行完毕后进入观察环节，观察报告会作为下一轮决策与最终综合的输入，形成闭环。整个工作流被持久化为一条工作流运行记录（AgentWorkflowRun）与若干任务运行记录（AgentTaskRun），支撑页面回看与问题排查。

#### 5.3.2 任务调度与并行执行设计

调度器的核心执行方法接收工作流规格后，进入"多轮执行循环"：每一轮首先执行任务图，然后调用观察智能体生成观察报告，随后判断是否需要重规划。任务图执行的具体策略为：将规格中的任务集合按依赖关系分层，依赖为空的任务立即并发执行；已完成任务的输出通过任务输入映射传递给下游任务；某任务失败时，其全部下游依赖任务直接标记为"跳过"（skipped），不再执行；每轮结束后把新增的任务结果合并到总结果集。

系统对任务执行者采用注册表设计：每种任务类型（仓库健康检查、缺陷分析、合并请求审查、构建排障、知识检索、安全风险检查等）注册为一个异步执行函数，复用第 5.2 节与第 5.4 节介绍的既有能力。这一设计使得新增任务类型无需改动调度框架，只需注册新的执行函数并扩展规划智能体的任务类型说明。

#### 5.3.3 有限重规划机制

规划不可能一次完美，工作流需要能够在执行过程中修订计划，但无限重规划会浪费资源并可能陷入震荡。系统采用"有限重规划"机制：

（1）重规划触发条件。每轮观察后，调度器根据任务结果与观察报告判断是否需要重规划，典型触发条件包括：出现失败任务且存在可替代路径、观察发现关键证据缺失但存在可补充的任务手段、观察发现结论冲突需要增加校验任务。

（2）重规划执行。触发后调用规划智能体的重规划方法，输入包括当前规格、全部任务结果、观察报告、重规划原因与迭代序号；重规划产出新的工作流规格，其中的新增任务需保留原有任务的既有结论作为上下文。

（3）收敛保护。系统为重规划次数设置上限（上限值可由运行配置指定）；每次重规划后比较新旧任务图，若任务集合与依赖关系未发生变化则终止重规划，防止"重规划了但计划没变"的空转；达到上限后停止重规划，直接进入综合环节，并把未解决事项交由综合智能体在结论中说明。

每轮的执行结果、观察报告与重规划事件（记录触发原因、任务数量变化与新增任务清单）都被收集进工作流报告，作为可审计的执行轨迹。

#### 5.3.4 观察与综合的检查设计

观察智能体执行的检查项可归纳为四类：其一，门禁检查——例如发布场景中的"是否存在失败构建""是否存在未解决的阻塞缺陷"等业务门禁条件是否满足；其二，冲突检查——不同智能体的结论之间是否存在互相矛盾的表述（例如构建排障结论为"可修复"而合并请求审查结论为"存在高风险改动"）；其三，证据检查——结论是否有对应的证据引用，证据是否来自可信来源且时效满足要求；其四，人工确认事项提取——需要人工决策的开放问题（如"某缺陷的优先级需要产品确认"）。

综合智能体在生成结论时遵循"有保留的结论"原则：当观察报告存在未解决冲突或证据缺口时，不给出绝对化建议，而是给出带条件的建议并显式列出待确认事项。工作流指标（任务数、成功/失败/跳过数、执行轮数、重规划次数、观察发现数、总耗时）随报告一并持久化，便于横向比较不同问题的执行成本。

### 5.4 检索增强生成模块

#### 5.4.1 研发数据分流策略

研发场景的数据具有异构、时效敏感两个特点，将全部数据统一向量化既浪费成本又引入"过期信息误用"风险。系统因此设计了三类数据的访问策略（研发数据分流）：

（1）当前代码。以代码工作区为权威来源，通过代码搜索与文件读取工具实时获取，保证分析基于最新检出而非历史快照。

（2）实时状态。缺陷、合并请求、构建运行等的状态字段与统计数据直接查询关系数据库或平台接口，保证"当前是否通过""当前是否关闭"等判断始终准确。

（3）历史非结构化知识。缺陷描述与讨论、合并请求说明与评审评论、失败构建日志、项目文档、上传知识文档以及经批准的长期记忆，进入检索增强生成链路做语义召回。

分流策略在提示层同步传达给模型：系统提示中明确"涉及当前状态与当前代码时需回到权威数据源核验，检索结果仅作为候选证据"。

#### 5.4.2 文档处理与索引设计

知识库创建时记录一组检索配置：嵌入模型（默认 Qwen3-Embedding-0.6B，向量维度 1024）、检索方式（默认混合检索）、是否启用重排及重排模型（默认 qwen3-rerank）、Top-K、分数阈值开关与阈值（默认 0.8）、切分块大小（默认 800 字符）与重叠长度（默认 100 字符）。配置以仓库为维度保存，同一仓库的全部检索请求使用一致配置，保证行为可复现。

文档处理流水线依次执行：格式解析（支持文本、Markdown、PDF、Word、JSON、CSV 与日志文件）→ 校验去重（按文件 SHA-256 跳过重复上传）→ 结构感知切分 → 嵌入计算 → 向量入库。切分环节不采用简单的定长截断，而是优先按文档结构（标题、段落、代码块、日志错误段）寻找切分边界，超长结构块再按块大小切分并保留重叠；每个文档块记录其所属父文档标识与序号，为"同一父文档最多入选两个块"的检索去冗余策略提供依据。

向量入库使用统一的 Milvus 集合，通过仓库标识与来源类型等隔离字段实现多仓库共存；集合名中携带嵌入模型信息（如 devflow_rag_qwen1024），避免不同向量空间的数据混用。嵌入服务支持本地推理与云端接口两种提供方式；当配置的嵌入依赖缺失时系统直接报错，而不是静默切换到另一套向量空间，保证检索质量问题的可解释性。

#### 5.4.3 混合检索设计

检索阶段采用"向量召回 + 关键词召回"双路并行：

（1）向量召回。将查询文本经嵌入模型映射为向量，在 Milvus 中按仓库过滤条件执行近邻检索，召回语义相近的候选文档块。

（2）关键词召回。在关系库中对文档块内容执行 BM25 评分检索[9]，参数取 k₁ = 1.5、b = 0.75。针对中文无空格分词的特点，词项处理同时生成单字与二元组（Bigram）词项，兼顾中文短语与英文标识符（如错误码、函数名）的匹配。

（3）元数据过滤。两路召回均支持附加过滤条件，包括标签、状态、文件路径前缀、时间范围与分支，用于将检索限定在处理中的对象范围内（例如"只检索与当前合并请求相关路径的讨论"）。

（4）近重复过滤。对候选集合执行基于 Jaccard 相似度的近重复检测（阈值 0.9），抑制相似度极高的重复块占据候选名额。

#### 5.4.4 融合、重排与引用设计

双路召回结果需要融合为统一排序。系统采用加权分数融合为主、排名奖励为辅的策略：向量路得分权重 0.62，关键词路得分权重 0.30（两路得分先各自归一化）；同时被两路召回的文档额外获得 0.08 的奖励分，体现"双路验证"的置信度加成。融合后执行两项去冗余：同一父文档最多保留两个块（MAX_CHUNKS_PER_PARENT = 2），避免单一长文档挤占证据位；再执行近重复过滤。之后对融合排序的前若干候选（默认最多 24 条）调用重排模型进行交叉编码打分[10]，按重排分数取最终 Top-K（默认 3 条）。

生成阶段将最终证据块按编号组织进提示词，要求模型"仅基于给定证据回答，并以编号标注每个结论的证据来源"；回答中的引用编号在前端渲染为可展开的证据卡片。系统同时实现答案门禁（Answer Gate）：当检索结果为空或全部低于分数阈值时，不进入生成阶段，直接返回"未检索到足够证据"的提示，并建议用户调整查询词或补充知识文档。

#### 5.4.5 对话链路中的双检索设计

在对话场景中，检索发生两次，形成互补：第一次是"预检索"，上下文组装器在调用对话智能体之前，按用户原始问题执行一次混合检索，将结果作为初始证据注入提示，使模型第一轮决策即有依据；第二次是"智能体检索"，模型在循环中可将知识检索作为工具调用，对查询词进行改写、按不同资料连续补查，并基于多轮检索结果交叉验证。预检索保证响应效率，智能体检索保证复杂问题的检索深度。

#### 5.4.6 召回测试与索引重建

为支持检索质量诊断，系统提供召回测试功能：用户输入测试查询后，系统返回各候选文档块的得分明细（向量分、关键词分、融合分、重排分与最终排名）与来源信息，并保存运行记录。当调整切分参数或嵌入模型后，可通过索引重建接口按新配置清理历史向量并重新处理全部知识文档；重建过程按仓库执行，且只处理本仓库数据，不影响其他仓库。

### 5.5 上下文管理与记忆系统

#### 5.5.1 分层上下文预算

长会话的关键矛盾是"历史信息价值"与"上下文窗口容量"之间的权衡。系统将输入预算（默认 24000 tokens，另预留 3000 tokens 给模型响应）按信息类别划分为五个区块并分配比例：系统提示占 12%、记忆摘要占 22%、检索证据占 34%、近期对话占 22%、工具结果占 10%。各类信息按各自额度裁剪：证据块按检索排名截断、工具结果按长度压缩、近期对话保留最近若干条消息。分层预算的优势在于任何一类信息膨胀都不会挤占其他类别的基本额度，例如一个返回超长日志的工具调用不会把证据区块完全挤出上下文。此外，相关研究表明语言模型对长上下文中部信息的利用效率明显低于开头与结尾位置[20]，因此系统对任务约束与证据等关键信息采用固定位置组织，减少位置效应对信息利用效果的影响。

#### 5.5.2 压缩触发机制

系统按 token 压力（已用值与预算的比值）分级触发压缩：当进入警戒区（阈值 20000）时仅告警并输出诊断信息；进入自动压缩区（阈值 13000）时执行常规压缩——将较早的对话轮次总结为摘要（默认摘要目标 1800 tokens），保留最近 8 条消息原文，对工具结果进行结构化压缩（保留关键字段与结论，截断原始数据）；压力进一步升高进入激进压缩区（阈值 8000）时，进一步压缩证据与记忆区块；在最紧张的手动压缩区（阈值 3000）下执行最大力度的压缩。压缩失败（如摘要调用出错）时按配置重试，连续失败达到上限（默认 3 次）后降级为直接截断并记录告警。压缩事件、压缩前后 token 估计与保留策略均记入诊断信息，保证压缩行为的可回溯。

#### 5.5.3 会话封存与项目记忆

当会话达到一定长度或用户主动触发时，系统执行会话封存：将对话转录（Transcript）与摘要固化到会话记录中，随后由记忆提取流程从封存内容中抽取结构化信息，更新到项目级线程记忆（ThreadMemory）。项目记忆采用结构化字段设计，包含：摘要、事实（Facts）、决策（Decisions）、开放问题（Open Questions）、任务（Tasks）、用户偏好（User Preferences）、仓库上下文（Repo Context）与引用（Citations）。相较于保存原始对话，结构化记忆的 token 占用更小、检索精度更高；后续会话开始时，记忆摘要作为上下文区块注入，使智能体"记得"项目的历史决策与待办事项。

#### 5.5.4 候选记忆与人工批准

并非所有从对话中抽取的信息都值得长期保存，错误结论一旦固化为长期记忆会被反复沿用。系统因此设计"候选记忆—人工批准"机制：记忆提取产出的条目首先进入候选记忆表（MemoryCandidate），状态为待审批（pending），附带来源会话与提取依据；用户在前端审查候选条目，批准（approved）后条目才进入记忆体系参与后续召回，拒绝的条目保留拒绝状态以备追溯。召回事件（RecallEvent）记录每次记忆检索的查询、范围、结果与引用，形成记忆使用情况的完整审计。

### 5.6 安全草稿与审计机制

#### 5.6.1 草稿生命周期设计

涉及外部系统写操作的能力（发表评论、创建或关闭缺陷、添加标签等）采用草稿机制承接，草稿实体（ActionDraft）的核心字段包括：草稿类型、目标类型与目标标识、标题与正文内容、风险级别、状态、创建人、确认人、执行时间与执行结果。草稿的生命周期状态流转为：待确认（pending_confirmation）→ 已确认执行（confirmed/executed）或取消；执行失败时记录错误信息且状态可重试。模型在对话中产生写操作意图时，调用安全风险分类工具评估风险级别，随后由安全智能体生成草稿正文；草稿以卡片形式返回对话界面，经用户核对与确认后，才由后端调用平台接口执行真实写操作。

#### 5.6.2 权限校验与审计

系统实现角色-动作维度的权限校验模块，在草稿确认执行与关键管理接口上强制校验当前用户的角色权限（如普通成员不允许执行关闭缺陷等高权限操作）。所有写操作与关键管理操作（同步、索引重建、草稿执行等）写入审计日志表（AuditLog），记录操作者、操作类型、目标对象、请求参数摘要、执行状态与结果，形成"谁在何时对什么执行了什么、结果如何"的完整记录链，满足事后审计与问题追溯需求。

#### 5.6.3 凭据安全

代码托管平台令牌等敏感凭据在持久化时使用对称加密存储（加密密钥由环境变量提供），接口返回时只回传"已配置/未配置"状态而不回传明文；日志系统在输出前对已知敏感字段做脱敏处理。环境变量为凭据的唯一推荐入口，开发演示模式下默认关闭真实写操作。

### 5.7 流式进度推送与运行轨迹

#### 5.7.1 SSE 事件流设计

对话与工作流的执行时间较长，采用 SSE 向客户端持续推送执行事件。事件类型覆盖执行全过程：运行开始与路由决策、模型决策摘要、工具调用开始（工具名与参数摘要）与调用结束（耗时与结果摘要）、工作流任务计划与各任务状态变化、答案文本分片、引用列表、运行结束（最终回答与统计）。前端按事件类型分别渲染到"执行轨迹"与"回答内容"两个区域，用户可以看到系统"正在做什么"，而不是面对一个长时间无响应的等待界面。SSE 相比 WebSocket 的实现更简单、对服务端更友好，且天然支持断线重连，符合本系统"服务端单向推送进度"的通信模式。

#### 5.7.2 运行轨迹持久化

系统的每次执行都在三个粒度留下持久化轨迹：对话运行（AgentRun）记录单次对话的用户消息、路由、完整工具调用序列与最终回答；工作流运行（AgentWorkflowRun）记录目标、规格、观察报告、最终结论与指标；任务运行（AgentTaskRun）记录每个任务的输入、结果、状态、错误与起止时间。三层记录通过外键关联，形成一个完整可回放的分析过程。当回答质量出现问题时，可以沿轨迹逐层检查：是工具参数有误、检索证据不足、任务结论冲突，还是综合阶段的组织问题，从而将"回答不好"这一模糊现象定位为具体环节的具体缺陷。

### 5.8 能力扩展机制

#### 5.8.1 基于 MCP 的外部工具接入

系统通过模型上下文协议（MCP）接入外部工具服务。MCP 定义了一套标准化的工具描述与调用协议，系统内部的 MCP 客户端负责连接外部服务、拉取工具清单并适配到统一的工具注册表；记忆服务即以 MCP 服务形式提供，使记忆工具的实现在协议层与其他工具解耦，可独立部署与升级。

#### 5.8.2 技能运行时

对于需要固定步骤与规范的稳定流程（如缺陷分诊流程、构建排障流程、安全草稿流程、周报流程等），系统实现了技能运行时（Skill Runtime）。每个技能以 SKILL.md 文件定义，内容包含适用条件、执行步骤、需要使用的工具白名单与输出规范。运行时按用户显式指定或消息触发条件激活技能：激活时校验技能声明的工具是否可用；任务执行期间只加载当前技能的完整指令与受限资源；技能的名称、版本、激活原因、指令摘要与执行校验结果记入运行轨迹。系统当前内置六类技能，覆盖缺陷分诊（issue-triage）、合并请求审查（pr-review）、构建排障（ci-debug）、项目调查（project-investigation）、安全草稿（safety-draft）与周报（weekly-report）。技能机制的价值在于把"提示词工程实践"沉淀为可版本化、可审计、可复用的资产。

### 5.9 前端界面实现

前端应用基于 Next.js 15 的 App Router 组织页面，使用 React Query 统一管理服务端状态与缓存，主要页面及其功能为：仓库页（仓库接入、同步与健康摘要）、对话页（流式对话与执行轨迹）、缺陷页与合并请求页（列表与单条分析）、持续集成页（运行列表与失败排障）、工作流记录页（多智能体工作流的回放）、知识库页与知识库详情页（文档管理与召回测试）、检索问答页（RAG 独立问答入口）、代码图页（代码符号与关系浏览）、草稿页（安全草稿的审查与确认）、评测页（评测任务提交、进度与结果对比）、报告页与工作区页等，共十七个路由页面。

交互实现上有三个要点：其一，流式渲染，对话接口以事件流方式读取，边接收边更新，答案分片与轨迹事件分别渲染，长回答不会阻塞界面；其二，异步任务语义，评测等后台任务在提交后以轮询方式跟踪进度，刷新或关闭页面不会中断任务；其三，证据可视化，回答中的编号引用渲染为可交互的证据卡片，展示来源类型、路径与原文片段，用户可快速核对结论依据。

### 5.10 本章小结

本章详细介绍了系统各模块的设计与实现。数据接入模块实现了五类研发数据的分页同步、五态同步状态管理与仓库健康检查；对话智能体模块基于状态图实现了工具调用循环与三重执行约束；多智能体工作流模块实现了"规划—调度—观察—综合"四角色协作、依赖驱动的并行调度与有限重规划；检索增强生成模块实现了研发数据分流、结构感知切分、双路混合召回、加权融合、重排与引用、召回测试；上下文与记忆模块实现了分层预算、分级压缩、会话封存与候选记忆人工批准；安全模块实现了草稿生命周期、权限校验与审计留痕；此外还介绍了流式推送、运行轨迹、MCP 与技能扩展以及前端界面的实现要点。

### 6.4 基于 RAGAS 的回答质量评估

#### 6.4.1 评估体系设计

功能测试验证的是"功能是否可用"，评测体系回答的是"回答是否变好"。系统建立了基于固定评测集的自动评估流程：评测在隔离会话中真实运行生产对话智能体与完整工具集，先收集预检索证据，再由智能体循环执行二次检索，最后统一收集回答、证据与工具轨迹，交由 RAGAS 框架[12]计算质量指标。评测结果持久化评测集哈希、阈值配置、逐题工具轨迹、检索证据、硬规则检查与失败诊断信息，使两次评测之间具备严格可比性。

#### 6.4.2 评估指标与验收门禁

评测指标分为语义质量指标与执行行为指标两组，各项指标及验收阈值如表6-4所示（阈值可在配置中调整，表中为默认值）。

**表6-4 评测指标与验收阈值**

| 指标 | 含义 | 默认阈值 |
|------|------|---------|
| 上下文精确率（Context Precision） | 检索到的证据中相关内容的占比 | ≥ 0.75 |
| 上下文召回率（Context Recall） | 标准答案所需证据被检索到的比例 | ≥ 0.80 |
| 忠实度（Faithfulness） | 回答内容忠实于检索证据、无编造的比例 | ≥ 0.90 |
| 答案相关性（Answer Relevancy） | 回答与问题的相关程度 | ≥ 0.80 |
| 智能体目标达成度（Agent Goal Accuracy） | 回答是否达成题目定义的预期目标 | ≥ 0.80 |
| 工具调用准确率（Tool Call Accuracy） | 工具调用行为与期望工具使用的一致性 | ≥ 0.90 |
| 工具调用 F1（Tool Call F1） | 工具调用行为的查准与查全综合值 | ≥ 0.90 |

整体通过要求"硬规则全部满足"且"五项语义指标均达到阈值"。硬规则检查确定性行为（如引用是否完整、输出结构是否合法、是否出现禁止内容），语义指标由模型裁判（Judge）评分。评测页面将"执行状态"与"质量状态"分离展示：低分是质量失败；裁判调用失败或指标缺失则属于评测不完整，不能伪装为质量结论——这一区分保证了评测结论本身的可靠性。

#### 6.4.3 回归对比与失败诊断

评测体系服务于持续迭代，具体设计了三条闭环路径：

（1）回归对比。用户可选择两个"评测集哈希、裁判配置与 Top-K 一致"的历史评测结果进行对比，页面逐题展示两次运行的指标变化与证据差异，回答"改动是否带来真实提升"。

（2）失败诊断。评测失败后可直接展开问题用例，查看实际回答、参考答案、检索来源、工具轨迹与可执行诊断建议，定位失败环节（检索未命中、工具选择错误、综合表述偏差等）。

（3）评测到工单的闭环。对确认由系统缺陷导致的失败用例，可一键生成"创建缺陷"类型的操作草稿，把失败用例、证据与建议带入人工确认流程，且不会直接写入平台——评测发现的问题以安全草稿方式进入改进流程，形成"评测—诊断—工单—修复—回归"的完整闭环。

（4）评分重试。裁判服务超时或个别指标缺失时，页面支持"仅重试异常评分"，复用已保存的回答与证据重新评分，不需要重跑对话智能体，节约重复推理成本。

### 6.5 本章小结

本章介绍了系统的测试与评估工作。首先说明了容器化测试环境的配置与四层测试策略；然后通过十二个代表性功能用例验证了数据接入、分析能力、协作决策、检索问答与安全机制等核心场景；随后介绍了覆盖主要后端链路的自动化测试体系；最后详细说明了基于 RAGAS 的回答质量评估设计，包括指标定义、验收阈值、回归对比、失败诊断与评测闭环。测试与评估结果表明，系统各功能实现符合需求定义，且具备可量化、可回归的质量保障能力。

## 第7章 总结与展望

### 7.1 全文总结

本文针对研发协作中"信息分散、证据收集成本高、复杂判断依赖资深经验"的现实问题，设计并实现了一个基于多智能体协作的研发协作系统。论文完成的主要工作如下：

（1）完成了系统需求分析与总体设计。在分析可行性、功能需求与非功能需求的基础上，提出了证据驱动、分层解耦、人机协同、安全可控、可观测与可评测五项设计原则，完成了五层总体架构、八个功能模块、数据库域划分与接口协议的设计。

（2）实现了研发数据接入与同步模块。支持五类研发数据的分页同步与覆盖范围报告，通过五种同步状态区分完整、为空、部分、失败与跳过情形，并实现部分失败的保留策略与定时同步，为系统提供可靠的数据底座。

（3）实现了基于原生工具调用的对话智能体。通过状态图组织"决策—工具执行—结果观察"循环，实现了最大步数、重复调用检测、八类工具错误分类处理与上下文溢出恢复等执行约束，保证智能体在可控边界内完成任务。

（4）实现了"规划—调度—观察—综合"多智能体工作流。通过依赖驱动的并行调度、失败跳过、结构化观察检查与有限重规划机制，支撑跨领域工程决策问题的系统化分析，并实现工作流级与任务级的完整运行轨迹持久化。

（5）实现了工程化检索增强生成链路。通过研发数据分流策略区分当前代码、实时状态与历史知识三类数据的访问方式；实现结构感知切分、向量与关键词双路召回、加权融合、重排、编号引用、按仓库隔离、召回测试与答案门禁。

（6）实现了上下文与记忆、安全执行与评测体系。包括分层上下文预算与分级压缩、会话封存与候选记忆人工批准、安全草稿生命周期与审计留痕，以及基于固定评测集与 RAGAS 指标的量化评估、回归对比与失败诊断闭环。

系统测试与评估表明，各功能模块实现符合设计预期，关键链路具备自动化验证与量化度量能力。本文的工作完整覆盖了"数据接入—知识检索—智能体协作—安全执行—效果评测"五个环节，对同类大语言模型应用系统的工程化落地具有参考价值。

### 7.2 不足与展望

受时间与条件限制，本系统仍存在以下不足，也是后续改进的方向：

（1）评测规模有限。当前固定评测集侧重研发问答的核心场景，题目数量与场景覆盖度仍有提升空间；后续可扩展多类型、多难度的评测集，并引入更细粒度的过程指标（如检索命中位置、多轮工具调用效率）。

（2）模型能力依赖。系统的分析质量与所接入模型的能力强相关，不同模型在工具调用稳定性与长上下文处理上差异明显；后续可研究模型路由与多模型协同策略，按任务类型选择适配模型，并加强弱模型下的降级路径设计。

（3）写操作自动化程度保守。安全草稿机制保证了安全性，但也使操作链路包含人工确认环节；后续可在风险分级基础上设计"低风险白名单自动执行 + 高风险人工确认"的差异化策略，在安全与效率间取得更好的平衡。

（4）多用户与权限体系较简单。当前系统的角色模型以满足演示与单团队使用为主；后续可完善多租户隔离、细粒度权限与团队协作能力。

（5）增量同步与数据规模。当前同步以分页全量拉取为主，随着仓库规模增长，可引入基于时间戳与变更事件的增量同步机制，并结合平台 Webhook 实现近实时更新。

总体而言，本文验证了多智能体架构在研发协作场景中的可行性，也展示了"证据驱动、人机协同、安全可控、可评测"这一设计思路的工程价值。随着大语言模型能力的持续演进，此类系统有望在研发效能提升中发挥越来越重要的作用。
