# 基于多智能体协作的研发协作系统设计与实现

## 摘要

在团队软件研发过程中，判断一次代码改动能否合入、定位持续集成失败的根因、评估缺陷优先级，往往需要同时查阅代码变更、缺陷描述、评审评论、构建日志与项目文档，而这些信息分散在代码仓库、项目管理平台、持续集成系统与团队知识库中，工程师需先花费大量时间收集整理上下文才能进入分析决策环节。大语言模型具备较强的语言理解与推理能力，但直接使用通用对话模型处理研发协作问题，仍存在证据来源不权威、上下文组织困难、分析深度不足与写操作安全风险高等问题。

针对上述问题，本文设计并实现了一个面向研发协作场景的多智能体系统。系统采用 Python 智能体后端与 Next.js 前端的全栈架构，划分为数据基础、知识与工具、智能协作、应用服务与用户五层结构。本文主要工作包括：第一，构建研发数据接入与同步模块，实现缺陷、合并请求、持续集成记录与评审评论等数据的同步与覆盖范围报告；第二，设计基于原生工具调用的对话智能体，以状态图组织“决策—工具执行—结果观察”循环，并实现最大步数、重复调用检测与工具错误分类等执行约束；第三，设计“规划—调度—观察—综合”多智能体工作流，支持依赖驱动的并行执行与有限重规划；第四，实现结构感知切分、双路混合召回、加权融合、重排与按仓库隔离的检索增强生成链路；第五，设计分层上下文预算、跨会话记忆、安全草稿与人工确认机制，以及基于 RAGAS 的回答质量评测体系。系统还采用“研发数据分流”策略：当前代码通过工作区工具读取，实时状态通过数据库查询，历史知识进入检索链路做语义召回，避免将过期信息当作事实。

系统在本地容器化环境中完成部署

系统在本地容器化环境中完成部署，功能与集成测试覆盖数据同步、智能体循环、工作流编排、检索链路、上下文压缩、项目隔离与安全确认等关键链路；基于固定评测集与 RAGAS 指标的评测体系可对回答质量进行量化，并支持回归对比与失败诊断。结果表明，该设计能够为缺陷分诊、合并请求审查、持续集成排障与版本发布检查等场景提供带证据的分析建议，并以安全草稿方式承接外部写操作，为研发协作类智能体系统的工程设计提供了一种可行方案。

**关键词：** 大语言模型；智能体；多智能体协作；检索增强生成；研发协作

## Abstract

In team software development, deciding whether a code change can be merged, diagnosing the root cause of a CI failure, or evaluating the priority of an issue usually requires reviewing code changes, issue descriptions, review comments, build logs and project documents at the same time. Such information is scattered across code repositories, project management platforms, CI systems and team knowledge bases, so engineers must spend considerable time collecting and organizing context before reaching the analysis and decision stage. Large language models (LLMs) have strong language understanding and reasoning capabilities, but directly applying a general-purpose chat model to development collaboration tasks still suffers from unauthoritative evidence, difficult context organization, insufficient depth for complex problems, and security risks in write operations.

To address these problems, this thesis designs and implements a multi-agent system for development collaboration scenarios. The system adopts a full-stack architecture with a Python agent backend and a Next.js frontend, and is organized into five layers: the data foundation layer, the knowledge and tool layer, the intelligent collaboration layer, the application service layer and the user layer. The main work of this thesis includes: first, a repository data ingestion and synchronization module that synchronizes issues, pull requests, CI runs, code files and review comments with pagination coverage reporting and status management; second, a conversational agent based on native tool calling, whose “decision–execution–observation” loop is organized as a state graph with execution constraints such as a maximum step limit, repeated-call detection and categorized tool error handling; third, a “plan–orchestrate–observe–synthesize” multi-agent workflow, in which the planner decomposes tasks and declares dependencies, the orchestrator executes ready tasks in parallel, the observer inspects evidence gaps and conflicting conclusions, and the synthesizer produces a unified recommendation, with bounded replanning; fourth, an engineered Retrieval-Augmented Generation (RAG) pipeline featuring structure-aware chunking, hybrid retrieval combining dense vectors and keyword search, weighted fusion, reranking, numbered citations, per-repository isolation and retrieval testing; fifth, a layered context budget and cross-session memory mechanism, a safety draft mechanism with human confirmation, and a RAGAS-based answer quality evaluation and regression verification system. In addition, the system adopts a “development data triage” strategy: current code is read through workspace tools, real-time status is queried from the database or APIs, and historical unstructured knowledge enters the RAG pipeline, avoiding treating outdated information as facts.

The system is deployed in a local containerized environment. Functional and integration tests cover key paths such as data synchronization, the agent loop, workflow orchestration, the retrieval pipeline, context compression, project isolation and safety confirmation. The evaluation system based on a fixed test suite and RAGAS metrics can quantify answer quality and support regression comparison and failure diagnosis against the same baseline. The results show that the design can provide evidence-backed analysis suggestions for issue triage, pull request review, CI debugging and release readiness checking, and can carry out external write operations through safety drafts, offering a feasible engineering approach for development collaboration agent systems.

**Key words:** large language model; agent; multi-agent collaboration; retrieval-augmented generation; development collaboration

## 第1章 绪论

本章首先阐述课题的研究背景与意义，随后梳理国内外相关研究现状，最后说明本文的主要研究内容与论文组织结构。

### 1.1 研究背景与意义

随着软件系统规模不断扩大与协作方式持续演进，软件研发活动已高度平台化、分布式化。一个中等规模的团队需要同时维护代码仓库、缺陷跟踪、合并请求（Pull Request，PR）评审、持续集成（Continuous Integration，CI）流水线与团队知识库等多个平台，而高频问题的答案往往需要跨平台交叉验证：判断代码改动能否合入，需要核对合并请求、关联缺陷、评审意见与检查结果；排查构建失败，需要从日志中提取关键错误并结合代码与历史文档判断原因。这些信息分散且数量庞大，仅“找齐背景与证据”就会消耗工程师大量时间，对项目新成员尤其困难。

大语言模型（Large Language Model，LLM）为解决该问题提供了新的技术路径，但直接使用通用对话模型处理研发协作问题存在明显不足：模型的参数化知识无法覆盖项目最新代码与实时状态，容易产生与事实不符的“幻觉”；研发问题涉及多源证据的比对，单轮问答难以完成系统性整合；简单堆砌对话历史会迅速耗尽上下文窗口；模型若被赋予直接操作外部系统的能力，误操作可能造成不可逆的影响。

智能体（Agent）范式将大语言模型从“文本生成器”升级为“任务执行者”：模型通过工具调用与外部环境交互，在“推理—行动—观察”循环中逐步收集证据、修正判断；当任务需要跨领域综合时，多智能体协作（Multi-Agent Collaboration）随之成为研究与工程实践的热点。本文正是在这一背景下，设计并实现了一个面向研发协作场景的多智能体系统：它连接代码仓库数据，支持缺陷分析、合并请求审查、持续集成排障与知识检索，并能以多智能体协作回答“版本能否发布”这类跨领域决策问题。本课题在工程层面完整覆盖数据接入、知识检索、智能体协作、安全执行与效果评测五个环节，探索大语言模型应用从“演示可用”走向“工程可靠”的关键设计，并对智能体循环、检索增强生成、多智能体调度与上下文管理等课题进行了梳理与实现验证。

### 1.2 国内外研究现状

围绕本文涉及的核心技术方向，本小节从大语言模型与智能体、检索增强生成、多智能体协作三个方面梳理国内外研究进展，并分析现有研发协作工具的不足。

#### 1.2.1 大语言模型与智能体技术

智能体技术的核心是让语言模型具备与外部环境交互的能力。Yao 等人的 ReAct 范式[1]将推理与行动交织进行，模型每步先生成思考轨迹，再决定调用何种工具并观察结果；Schick 等人的 Toolformer[2]验证了模型可通过自监督方式学会调用外部工具；Mialon 等人的综述[3]将“推理、工具、记忆”归纳为语言模型增强的三条主线。工程实践层面，LangChain[4]统一了模型、工具与消息抽象，LangGraph[5]以状态图（State Graph）显式建模执行流程、分支与停止条件，使多轮工具调用具备可控边界。

#### 1.2.2 检索增强生成技术

检索增强生成（Retrieval-Augmented Generation，RAG）由 Lewis 等人系统提出[6]，核心思想是在生成回答前先检索外部知识，将证据与问题一同交给模型，以缓解幻觉并提升可溯源性与时效性。检索技术经历了从稀疏到稠密、再到混合检索的演进：BM25 基于词项频率与文档长度归一化计算相关性[7]；稠密段落检索（DPR）[8]用双塔结构将问题与文档映射到同一向量空间；倒数排名融合（RRF）[9]为多路结果融合提供了简单有效的方法；交叉编码器重排[10]进一步提升排序质量。Gao 等人的综述[11]将 RAG 归纳为朴素、高级与模块化三个阶段，指出工程化 RAG 需在切分、检索、重排与评测环节系统设计。评测方面，RAGAS 框架[12]从上下文精确率、召回率、忠实度与答案相关性等维度实现自动化评估。

#### 1.2.3 多智能体协作技术

多智能体协作将复杂任务拆解给多个职责明确的智能体。Park 等人的生成式智能体[13]通过记忆、反思与规划机制验证了多智能体架构的潜力；Wu 等人的 AutoGen[14]以“可对话智能体”为核心抽象，支持多智能体协作并允许人类介入；MetaGPT[15]与 ChatDev[16]将软件团队角色映射为智能体，通过标准化中间产物传递信息，展示了多智能体在软件工程流程中的可行性。总体来看，现有研究多聚焦任务生成与流程模拟，面向真实研发数据的协作分析系统及配套的证据校验、冲突控制与安全机制仍有较大探索空间。

#### 1.2.4 现有研发协作工具的不足

当前研发协作领域已有若干工具化实践：代码托管平台内置了静态检查与自动评审能力，集成开发环境中的编程助手可以补全代码、解释片段。但这类工具多聚焦“代码本身”，对“跨平台信息收集与判断”的支持仍然有限：缺陷、评审讨论、构建日志与项目文档之间的关联未被有效利用；分析结论缺少可核查的证据链；面对“该不该合入”“该不该发布”这类综合决策，缺乏系统性的多智能体分工机制；自动写操作也缺乏草稿确认、权限校验与审计留痕等安全设计。上述不足正是本文工作试图填补的空间。

### 1.3 主要研究内容

围绕上述目标，本文的主要研究内容包括以下五个方面：

（1）研发数据接入与同步。实现代码仓库数据的连接、分页同步与状态管理，将缺陷、合并请求、评审评论、持续集成运行记录与日志等数据统一落库，并提供同步覆盖范围报告与仓库健康检查，为后续分析提供可靠的数据底座。

（2）对话智能体与工具调用循环。基于原生工具调用机制设计对话智能体，通过状态图组织“决策—工具执行—结果观察”的多轮循环，并实现工具参数校验、最大步数与重复调用限制、工具错误分类与重试等执行约束。

（3）多智能体协作工作流。设计“规划—调度—观察—综合”四角色协作架构，支持依赖驱动的并行调度、失败跳过、证据缺口与结论冲突检查，以及有限重规划机制。

（4）工程化检索增强生成链路。设计研发数据分流策略与文档处理流水线，实现结构感知切分、双路混合召回、加权融合、重排、编号引用、按仓库隔离与召回测试，并处理“证据不足时拒答”的答案门禁问题。

（5）上下文管理、安全执行与效果评测。设计分层上下文预算与压缩、跨会话记忆的人工批准、写操作的安全草稿与审计机制，以及基于 RAGAS 指标的量化评测与回归对比体系。

## 第2章 相关技术基础

本章对系统设计与实现所依赖的关键技术进行介绍，为后续章节的方案设计提供技术基础。

### 2.1 大语言模型与提示工程

本小节介绍大语言模型的基本原理，以及提示工程与结构化输出的相关概念。

#### 2.1.1 大语言模型基本原理

本文所依托的大语言模型以 Transformer 架构[17]为基础，完全基于自注意力机制（Self-Attention）建模序列中任意两个位置之间的依赖关系，具备良好的并行训练能力与长距离依赖建模能力，其核心计算如式（2-1）所示：

Attention(Q, K, V) = softmax(QKᵀ / √d_k)V　　（2-1）

其中 Q、K、V 分别表示查询矩阵、键矩阵与值矩阵，d_k 为键向量的维度。大语言模型的训练分为两个阶段：预训练阶段在海量文本上以自回归方式学习下一个词的预测，获得通用的语言能力与世界知识[18]；指令微调与基于人类反馈的强化学习（RLHF）阶段[19]通过人工标注的指令与偏好数据对模型进行对齐。经过两阶段训练的模型具备零样本与少样本学习能力，能够按自然语言指令完成多种任务，这是构建智能体系统的能力基础。

#### 2.1.2 提示工程与结构化输出

提示工程（Prompt Engineering）指通过设计输入提示来引导模型产生期望输出的方法。Wei 等人的思维链（Chain-of-Thought）提示[20]表明，引导模型先给出推理过程再给出结论，可以显著提升复杂推理任务的表现。在工程系统中，模型输出还需要被程序消费，本文系统采用结构化输出（Structured Output）方案：通过 Pydantic 模型定义输出 Schema，要求模型以 JSON 格式返回结果并在运行时进行类型校验，不符合 Schema 时可触发重试或降级，使分析结果可直接入库、渲染与二次加工，提高了系统鲁棒性。

### 2.2 工具调用与智能体循环

工具调用（Tool Calling）是模型与外部系统交互的标准化接口。系统向模型声明可用工具及其参数 Schema，模型决定是否调用及传入参数；系统执行工具后将结果回传，模型继续决策，直至任务完成或触发停止条件。这一“决策—执行—观察”的循环即智能体循环（Agent Loop），其概念源头可追溯到 ReAct 范式[1]。健壮的循环需要解决四类工程问题：循环停止条件（任务完成、最大步数上限、重复调用检测）；工具错误分类处理（重试、降级或终止）；过长工具结果的截断与压缩；敏感工具的权限校验与人工确认。

### 2.3 LangChain 与 LangGraph 编排框架

LangChain[4]提供了模型、消息、工具等核心抽象，统一了不同模型厂商接口的调用方式；本文的对话智能体基于其工具抽象注册工具集，通过 OpenAI 兼容接口接入模型服务。LangGraph[5]进一步提供基于状态图（State Graph）的编排能力：将执行过程建模为节点（Node）与边（Edge），节点表示计算步骤，边表示流转条件；相比线性链式调用，其分支与循环显式可查、执行状态统一管理、支持中断与恢复。本文系统以状态图组织对话智能体的执行循环，使多轮循环的停止条件具备显式、可控的结构。

### 2.4 检索增强生成

检索增强生成（RAG）由 Lewis 等人提出[6]，流程可概括为三个阶段：索引阶段将知识文档解析切分为文本块（Chunk），经嵌入模型映射为向量并存入向量数据库；检索阶段将问题映射为向量检索相近文本块，并同时执行关键词检索、对多路结果融合与重排；生成阶段将证据片段与问题组织进提示词，引导模型基于证据回答并标注引用来源。RAG 在本文系统中定位为“历史与非结构化知识的语义召回通道”，与工作区代码检索、数据库结构化查询共同构成三类证据来源，详见第5.4节。

### 2.5 混合检索与重排技术

单一检索路径存在固有局限：稀疏检索（如 BM25）依赖词项匹配，擅长捕获专有名词、错误码等精确信号，但无法理解语义改写；稠密检索基于语义向量，擅长同义表达，但对罕见词的区分度较低，工程实践因此普遍采用混合检索（Hybrid Retrieval）。BM25 评分函数如式（2-2）所示：

Score(q, d) = Σ IDF(q_i) · (f(q_i, d) · (k₁ + 1)) / (f(q_i, d) + k₁ · (1 − b + b · |d| / avgdl))　　（2-2）

其中 f(q_i, d) 为词项 q_i 在文档 d 中的出现频次，|d| 为文档长度，avgdl 为平均文档长度，k₁ 与 b 分别控制词频饱和程度与长度归一化强度[7]。多路召回结果的融合方法中，倒数排名融合（RRF）[9]仅依赖排名位置而非原始分数，避免了不同打分体系不可比的问题，其公式如式（2-3）所示：

RRF(d) = Σ 1 / (k + rank_i(d))　　（2-3）

其中 rank_i(d) 为文档 d 在第 i 路召回中的排名，k 为平滑常数；本文系统在实现中同时引入了带权重的分数融合与双路命中奖励策略（详见第5.4.4节）。重排（Rerank）阶段使用交叉编码器（Cross-Encoder）模型对候选与问题做联合编码打分[10]，能够建模问题与文档之间的细粒度交互，排序精度更高，但计算开销大，因此通常只对召回阶段的 Top-N 候选进行重排，从中筛选最终的 Top-K 证据。

### 2.6 系统开发与部署技术

系统后端采用 Python 与 FastAPI，其类型注解依赖注入与 Pydantic 校验降低了接口层开发成本；数据访问层使用 SQLAlchemy ORM，数据库为 PostgreSQL 16（配合 pgvector 扩展）；向量检索使用 Milvus 分布式向量数据库[21]，支持大规模向量相似性检索，并通过分区与标量过滤满足多租户隔离；前后端实时进度推送采用服务器发送事件（SSE）协议，相比轮询延迟更低、服务端开销更小。前端采用 Next.js 15 与 React 19，使用 TypeScript 与 Tailwind CSS，数据获取与缓存采用 TanStack React Query。系统通过 Docker Compose 将 PostgreSQL、Milvus、etcd、MinIO 等基础服务容器化，后端与前端以本地进程运行，配置项通过环境变量统一管理。

### 2.7 本章小结

本章介绍了本文所涉及的关键技术基础，包括大语言模型与提示工程、工具调用与智能体循环、LangChain 与 LangGraph、检索增强生成、混合检索与重排以及系统开发与部署技术，为后续章节的系统设计提供技术依据。

## 第3章 系统需求分析

### 3.1 系统设计目标与可行性分析

本小节明确系统的总体设计目标，并从技术、经济与操作三个方面进行可行性分析。

#### 3.1.1 系统设计目标

本系统的总体目标是：面向软件研发协作场景，构建一个能够连接代码仓库数据、理解研发上下文、提供带证据分析建议的智能协作系统。具体目标包括：

（1）数据连通性。打通代码仓库中缺陷、合并请求、持续集成、代码与文档等多源数据，建立统一的本地数据底座，使分析活动不再依赖人工跨平台收集信息。

（2）分析专业性。针对缺陷分诊、合并请求审查、持续集成排障三类高频任务设计专用分析能力，输出分类、优先级、风险点、修复建议等结构化结论。

（3）协作系统性。对“版本能否发布”等跨领域综合问题，提供规划、执行、观察、综合四角色协作机制，并显式处理证据缺口与结论冲突。

（4）证据可溯源。所有结论必须附带证据来源（代码位置、缺陷编号、日志片段、文档引用），检索范围按仓库隔离，检索不到证据时如实说明而不是编造。

（5）执行安全性。涉及外部写操作的能力采用“草稿—人工确认—执行—审计”流程，保证智能体具备执行能力但不越权。

（6）效果可度量。建立固定评测集与量化指标体系，使回答质量可测量、改动效果可回归对比。

#### 3.1.2 可行性分析

技术可行性方面，系统所依赖的大语言模型经 OpenAI 兼容接口接入，可灵活切换；FastAPI、PostgreSQL、Milvus、LangChain 与 LangGraph、Next.js 等技术均有成熟的社区生态；工具调用、SSE 推送、结构化输出等关键机制均有标准实现范式，技术风险可控。

经济可行性方面，系统全部基于开源组件构建，基础服务可通过 Docker 在单机环境部署；模型调用成本与使用量成正比，在开发与中小团队使用规模下成本较低。

操作可行性方面，系统以 Web 应用形式呈现，提供仓库管理、对话、分析结果、评测等图形化页面，同步、分析、评测等操作均可在页面一键触发，研发人员无需了解内部实现即可使用，交互成本低。

### 3.3 非功能需求分析

（1）安全性需求。访问凭据仅通过环境变量或用户输入提供，持久化时加密存储，日志不得打印令牌明文；写操作必须经过草稿与人工确认；关键操作记录审计日志；检索与问答按仓库隔离，防止跨仓库数据泄露。

（2）性能需求。同步接口支持分页与数量上限控制，避免大仓库同步阻塞服务；对话链路通过流式推送保证响应性；工作流为单任务设置超时上限（90 秒），避免个别任务挂起拖垮整体；上下文设置 token 预算（默认输入上限 24000 tokens），保证长会话不超过模型窗口。

（3）可观测性需求。每次对话记录工具调用序列、引用来源与最终回答；工作流持久化工作流级与任务级运行记录（含耗时、成功/失败/跳过统计、重规划次数）；关键链路输出结构化日志，便于定位“工具参数错误、检索证据不足、任务结论冲突”等典型问题。

（4）可扩展性需求。提供标准化工具扩展机制，支持通过模型上下文协议（MCP）接入外部工具；支持将稳定流程沉淀为技能（Skill）并按需激活；工作流任务类型可注册扩展，新增分析能力无需改动调度框架。

（5）可用性需求。前端覆盖仓库管理、对话、分析结果、评测等主要功能；长耗时操作展示执行进度；错误信息以用户可理解的方式呈现并给出恢复建议。

## 第4章 系统总体设计

本章阐述系统的总体设计，依次介绍设计目标与原则、总体架构、功能模块划分、数据库设计、接口设计与部署架构设计。

### 4.1 设计目标与原则

结合第3章的需求分析，系统的总体设计遵循以下五项原则：

（1）证据驱动原则。所有分析结论必须建立在可核查的证据之上。系统区分三类证据来源并采用不同访问方式：当前代码以代码工作区为权威来源，通过文件工具实时读取；缺陷、合并请求、持续集成等实时状态以数据库或平台接口为权威来源，通过结构化查询获取；历史文档、讨论与经验通过检索增强生成召回。这一“研发数据分流”策略避免了用过期文档解释当前代码、用历史讨论判断最新状态。

（2）分层解耦原则。系统自下而上划分为数据基础、知识与工具、智能协作、应用服务与用户五个层次，层间通过明确定义的接口交互，模型、编排、工具、存储各自独立演进，例如更换模型不影响工具层、新增工具不影响前端。

（3）人机协同原则。系统定位为“助手”而非“替代者”：分析类能力以建议形式输出，写操作只生成草稿、经人工确认后执行；工作流计划确认、记忆批准、草稿确认等关键节点均保留人工决策入口。

（4）安全可控原则。执行约束（最大步数、超时、重规划上限）、权限校验与审计日志在框架层统一实现，不依赖提示词的“自觉”；所有外部写操作默认关闭、显式启用。

（5）可观测与可评测原则。每次运行都留下轨迹（工具调用、任务结果、指标），回答质量通过固定评测集持续度量，使系统改进有量化依据。

### 4.2 总体架构设计

系统采用“Python 智能体后端 + Next.js 前端”的全栈架构，自下而上分为数据基础层、知识与工具层、智能协作层、应用服务层与用户层五个层次，总体架构如图4-1所示。

![图4-1 系统总体架构图](figures/fig4-1.png)

（1）数据基础层。负责数据持久化与版本管理，包括 PostgreSQL（仓库、缺陷、合并请求、会话、运行记录等结构化数据）、Milvus（知识文档块向量索引）与 Git 工作区（仓库代码的本地检出，为代码读取与检索提供对应版本快照）。

（2）知识与工具层。为智能体提供获取信息与执行动作的能力，包括代码工作区工具、平台接口工具、检索增强生成工具、记忆工具与安全工具；并通过模型上下文协议（MCP）与技能运行时（Skill Runtime）支持外部能力接入与稳定流程复用。

（3）智能协作层。系统的核心层，由对话智能体与多智能体工作流组成：对话智能体负责理解问题、选择工具、组织证据并生成回答；涉及跨领域综合决策时，任务转交工作流——规划智能体拆解任务，调度器按依赖调度执行，观察智能体检查证据与冲突，综合智能体汇总结论。

（4）应用服务层。由 FastAPI 应用构成，负责接收请求、校验参数、确定仓库与会话上下文、调用智能协作层执行、通过 SSE 推送执行进度，并保存会话记录与运行轨迹。

（5）用户层。由 Next.js 前端应用构成，用户在此选择仓库与会话、提交分析问题、查看流式执行进度与分析结果、管理知识库与评测任务。

一次典型请求的流转过程为：用户提交问题后，上下文组装器组织仓库信息、历史对话、相关记忆与预检索证据；对话智能体判断所需工具并执行调用；若需要综合分析则进入多智能体工作流完成分工分析与汇总；结果返回前端的同时，会话记录、工具调用与运行轨迹持久化到数据基础层，可复用的项目经验经确认后进入记忆体系供后续召回。

### 4.4 数据库设计

以缺陷表与工作流任务表为例说明关键字段设计。缺陷表（issues）包含仓库外键、平台缺陷编号、标题、正文、状态、标签（JSON）、作者、指派人与各时间戳字段，其中仓库外键与编号建立组合索引以支持按仓库快速查询。多智能体任务表（agent_task_runs）包含所属工作流外键、任务标识、智能体名称、任务类型、输入快照（JSON）、结果（JSON）、状态、错误信息与起止时间；任务结果以 JSON 保存，兼容不同任务类型的异构输出，同时保留状态与错误列以支持按状态检索与统计。

#### 4.4.3 索引与隔离设计

为支撑常见查询模式，系统在仓库外键、平台编号、状态、时间等高频过滤字段上建立索引；会话与仓库删除时通过级联约束清理从属数据。知识文档表通过仓库标识与来源类型标签实现检索隔离：检索时强制附加仓库过滤条件，保证一个仓库的分析只能召回本仓库的知识，这一点在测试中通过专门的项目隔离用例进行验证。

## 第5章 系统详细设计与实现

本章按照模块划分，依次介绍研发数据同步、对话智能体、多智能体工作流、检索增强生成、上下文与记忆、安全草稿、流式推送与运行轨迹、能力扩展以及前端交互的详细设计与实现。

### 5.1 研发数据接入与同步模块

本小节依次介绍仓库管理、数据同步流程与仓库健康检查三个部分的设计与实现。

#### 5.1.1 仓库管理设计

仓库是系统中所有数据的组织边界。仓库实体记录了代码托管平台类型、完整名称、克隆地址、本地检出路径与检出模式等信息。系统支持两种检出模式：“托管模式”下由系统管理仓库代码的本地副本，配合工作区管理器在后台完成拉取与版本更新；“本地模式”下直接指向用户机器上已有的代码目录，避免重复占用磁盘。仓库记录还保存最近同步时间与同步元数据（JSON），元数据中记录了每类数据源的覆盖范围，为仓库健康检查提供依据。

#### 5.1.2 同步流程设计

数据同步的总体流程为：接收同步请求并解析参数（数据源选择与数量上限）→ 按分页调用平台接口拉取数据 → 逐类落库（新增或更新）→ 生成同步报告 → 更新同步元数据与最近成功同步时间。同步覆盖五类主数据：缺陷、合并请求（含变更文件）、评审评论、持续集成运行记录（含任务与步骤明细）以及失败运行的日志文本。同步接口的 limit 参数表示“每类主记录的总数上限”：省略或传空表示读取全部分页，达到上限且存在后续记录时标记为“部分覆盖”；首次接入默认只取少量记录，定时同步默认读取全部分页。

同步状态机包含五种状态：completed（完整完成）、empty（请求成功但为空）、partial（达到上限或部分来源失败）、failed（所选主接口全部失败）与 skipped（未选择数据源）。状态判定的关键设计是“部分失败保留已有明细”：某一数据源失败时，不影响其他数据源已写入的数据，且不更新最近成功同步时间，使健康检查能够识别数据陈旧风险。自动同步由后台调度器实现：按配置的间隔（默认 300 秒）扫描需要同步的仓库，调用同一套同步服务完成数据更新，保证数据接近最新状态。

#### 5.1.3 仓库健康检查

健康检查模块对仓库数据执行三项校验：数据是否为空、同步是否完整（是否存在 partial/failed 状态的数据源）、数据是否在时效窗口内（最近成功同步时间是否超过 24 小时）；三项校验结果与统计数据共同构成仓库健康摘要。该摘要同时作为证据质量的判断依据：工作流执行分析时，若健康检查发现数据不足或陈旧，观察智能体会阻止基于该数据给出“可推进”的结论并要求先完成同步，体现了“不基于不完整证据下结论”的原则。

### 5.2 对话智能体与工具调用循环

本小节介绍对话智能体的总体结构、执行循环机制、执行约束设计以及上下文溢出的恢复策略。

#### 5.2.1 智能体总体设计

对话智能体（ChatAgent）是系统的统一入口，接收用户消息与运行上下文，使用原生工具调用机制选择下一步动作，直至生成最终回答或触发停止条件。其工具集共十四项，分为五类：证据与记忆类（研发证据检索、线程记忆读取等）、代码工作区类（文件列举、读取与搜索）、知识检索类（相似文档检索）、专用分析类（仓库健康摘要、缺陷分析、合并请求审查、构建排障、周报生成与安全风险分类）以及工作流入口（工程评审工作流）。工具集设计体现了“简单问题直接查、专项问题专办、复杂问题协作办”的分层策略。

#### 5.2.2 基于状态图的执行循环

执行循环以状态图实现，包含模型决策与工具执行两类节点及条件边；状态对象载明消息、工具映射、观察结果、工具调用记录、引用、步骤计数、停止原因与上下文统计等字段。每轮循环步骤为：组装本轮提示（系统提示、压缩后的历史上下文、预检索证据与本轮用户消息）；模型决策节点调用大语言模型，返回自然语言内容或工具调用请求；若请求工具调用，则进入工具执行节点——校验参数、执行工具、收集结果并生成观察记录，随后回到模型决策节点继续循环；若未请求，则视为任务完成，输出最终回答与引用。执行循环的整体流程如图5-1所示。循环中间事件通过流式通道实时推送，并在运行结束后持久化。

![图5-1 对话智能体执行循环流程图](figures/fig5-1.png)

#### 5.2.3 执行约束设计

为防止循环失控并提升鲁棒性，循环层实现了三重约束：

（1）步数上限。单次运行最多执行 12 步（max_steps = 12），达到上限时强制停止并基于已有观察生成收束性回答。

（2）重复调用限制。同一工具以相同参数被调用超过 2 次（max_repeated_tool_calls = 2）时判定为无效循环，终止运行并在回答中说明原因，避免模型在证据不足时反复重试同一查询。

（3）工具错误分类与重试。工具错误划分为八类：未知工具、超时、触发限流、瞬时网络故障、权限拒绝、数据不存在、模型输出非法与工具运行时错误；瞬时性错误（超时、限流、网络故障）允许重试一次（tool_retry_attempts = 1），确定性错误（权限、数据不存在、参数非法）不重试，而是将错误信息作为观察回传模型，由模型调整策略或向用户说明。

此外，工具调用参数通过结构化模型校验，非法参数在进入工具实现前即被拦截；模型调用侧设置温度参数为 0、超时 60 秒，并启用提示词缓存以降低重复系统提示的调用成本与延迟。

#### 5.2.4 上下文溢出恢复

长会话或大工具结果可能使请求超出模型上下文窗口，系统在两类时机防护：一是请求组装阶段的 token 预算裁剪（见第5.5节）；二是发生上下文溢出错误时，捕获并执行一次“溢出恢复”——对历史与工具结果更激进地重压缩后重试，同时把恢复动作记入运行状态，保证恢复过程可观测、不无限重试。

### 5.3 多智能体协作工作流

本小节依次介绍工作流的总体架构、任务调度与并行执行、有限重规划机制以及观察与综合环节的检查设计。

#### 5.3.1 工作流总体设计

多智能体工作流用于处理“版本能否发布”“合并请求能否合入”这类需要跨领域综合判断的问题，采用“规划—调度—观察—综合”四角色架构：

（1）规划智能体（PlannerAgent）。将用户目标拆解为边界明确的任务清单，生成工作流规格（WorkflowSpec）；每个任务声明其标识、任务类型、所需输入与依赖关系，并给出整体验收标准。

（2）调度器（WorkflowOrchestrator）。负责执行任务图：反复扫描未完成任务，收集依赖已满足的任务并行执行，直至全部完成；同时承担超时控制（单任务 90 秒）、失败处理与重规划驱动。

（3）观察智能体（ObserverAgent）。在所有可执行任务完成后，检查任务输出中的合并门禁（Merge Gate）条件、跨智能体结论冲突、低置信度结论、证据缺失与需要人工确认的事项，输出结构化观察报告。

（4）综合智能体（SynthesisAgent）。基于工作流规格、全部任务结果与观察报告，生成统一的决策备忘录，包含结论、依据、风险与建议的后续动作。

工作流的总体流程如图5-2所示。每一轮（Round）执行完毕后进入观察环节，观察报告作为下一轮决策与最终综合的输入，形成闭环；整个工作流被持久化为一条工作流运行记录（AgentWorkflowRun）与若干任务运行记录（AgentTaskRun），支撑页面回看与问题排查。

![图5-2 多智能体协作总体流程图](figures/fig5-2.png)

#### 5.3.2 任务调度与并行执行设计

调度器的核心执行方法接收工作流规格后，进入“多轮执行循环”：每一轮先执行任务图，再生成观察报告，随后判断是否需要重规划。任务图执行策略为：任务集合按依赖关系分层，依赖为空的任务立即并发执行；已完成任务的输出通过输入映射传递给下游任务；某任务失败时其全部下游任务标记为“跳过”（skipped）；每轮结束后把新增结果合并到总结果集。任务执行者采用注册表设计：每种任务类型（仓库健康检查、缺陷分析、合并请求审查、构建排障、知识检索、安全风险检查等）注册为异步执行函数，新增任务类型无需改动调度框架。

#### 5.3.3 有限重规划机制

规划不可能一次完美，工作流需要能够在执行过程中修订计划，但无限重规划会浪费资源并可能陷入震荡，因此系统采用“有限重规划”机制：

（1）重规划触发条件。每轮观察后，调度器根据任务结果与观察报告判断是否需要重规划，典型条件包括：出现失败任务且存在可替代路径、关键证据缺失但存在可补充的任务手段、结论冲突需要增加校验任务。

（2）重规划执行。触发后调用规划智能体的重规划方法，输入当前规格、全部任务结果、观察报告、重规划原因与迭代序号；产出的新规格中，新增任务保留既有结论作为上下文。

（3）收敛保护。系统为重规划次数设置上限（可由运行配置指定）；每次重规划后比较新旧任务图，若任务集合与依赖关系未变化则终止重规划，防止“重规划了但计划没变”的空转；达到上限后停止重规划直接进入综合环节，未解决事项由综合智能体在结论中说明。

每轮的执行结果、观察报告与重规划事件均被收集进工作流报告，作为可审计的执行轨迹。

#### 5.3.4 观察与综合的检查设计

观察智能体的检查项可归纳为四类：门禁检查（如“是否存在失败构建”“是否存在未解决的阻塞缺陷”等发布门禁）、冲突检查（不同智能体结论之间是否存在矛盾表述）、证据检查（结论是否有对应证据引用，来源是否可信、时效是否满足）与人工确认事项提取。综合智能体遵循“有保留的结论”原则：当观察报告存在未解决冲突或证据缺口时，不给出绝对化建议，而是给出带条件的建议并显式列出待确认事项。工作流指标（任务数、成功/失败/跳过数、执行轮数、重规划次数、观察发现数与总耗时）随报告一并持久化，便于比较不同问题的执行成本。

### 5.4 检索增强生成模块

本小节按照数据进入检索链路的先后顺序，依次介绍研发数据分流、文档处理与索引、混合检索、融合与重排以及召回测试等环节的设计。

#### 5.4.1 研发数据分流策略

研发场景的数据具有异构、时效敏感的特点，将全部数据统一向量化既浪费成本又引入“过期信息误用”风险，系统因此设计三类数据的访问策略：当前代码以代码工作区为权威来源，通过代码搜索与文件读取工具实时获取；实时状态（缺陷、合并请求、构建运行的状态与统计）直接查询数据库或平台接口；历史非结构化知识（缺陷讨论、评审评论、失败日志、项目文档、上传文档与经批准的长期记忆）进入检索增强生成链路做语义召回。分流策略同步传达给模型：涉及当前状态与代码时需回到权威数据源核验，检索结果仅作为候选证据。

#### 5.4.2 文档处理与索引设计

知识库创建时记录一组检索配置：嵌入模型（默认 Qwen3-Embedding-0.6B，向量维度 1024）、检索方式（默认混合检索）、重排开关与模型（默认 qwen3-rerank）、Top-K、分数阈值（默认 0.8）、切分块大小（默认 800 字符）与重叠长度（默认 100 字符）；配置以仓库为维度保存，保证行为可复现。文档处理流水线依次为：格式解析（支持常见文本、PDF、Word 与结构化格式）→ 校验去重（按 SHA-256 跳过重复）→ 结构感知切分 → 嵌入计算 → 向量入库。切分优先按文档结构（标题、段落、代码块、日志错误段）寻找边界，超长块再按大小切分并保留重叠；每个块记录所属父文档标识与序号，为“同一父文档最多入选两个块”的去冗余策略提供依据。向量入库使用统一 Milvus 集合，以仓库标识与来源类型等隔离字段实现多仓库共存，集合名携带嵌入模型信息，避免不同向量空间数据混用；嵌入依赖缺失时系统直接报错而非静默切换向量空间，保证检索质量问题的可解释性。

#### 5.4.3 混合检索设计

检索阶段采用“向量召回 + 关键词召回”双路并行：

（1）向量召回。将查询文本经嵌入模型映射为向量，在 Milvus 中按仓库过滤执行近邻检索，召回语义相近的候选块。

（2）关键词召回。在关系库中对文档块执行 BM25 评分检索[7]，参数取 k₁ = 1.5、b = 0.75；针对中文无空格分词的特点，词项处理同时生成单字与二元组（Bigram），兼顾中文短语与英文标识符（如错误码、函数名）的匹配。

（3）元数据过滤。两路召回均支持标签、状态、文件路径前缀、时间范围与分支等过滤条件，将检索限定在处理中的对象范围内。

（4）近重复过滤。对候选集执行基于 Jaccard 相似度的近重复检测（阈值 0.9），抑制相似度极高的重复块占位。

#### 5.4.4 融合、重排与引用设计

双路召回结果融合为统一排序，采用加权分数融合为主、排名奖励为辅的策略：向量路权重 0.62，关键词路权重 0.30（得分各自归一化），双路同时召回的文档额外获得 0.08 奖励分，体现“双路验证”的置信度加成。融合后执行去冗余：同一父文档最多保留两个块（MAX_CHUNKS_PER_PARENT = 2），并再次执行近重复过滤。随后对前若干候选（默认最多 24 条）调用重排模型交叉编码打分[10]，取最终 Top-K（默认 3 条）。生成阶段将证据块按编号组织进提示词，要求模型仅基于给定证据回答并以编号标注证据来源，引用在前端渲染为可展开的证据卡片。系统同时实现答案门禁（Answer Gate）：检索结果为空或全部低于阈值时不进入生成阶段，直接返回“未检索到足够证据”并建议调整查询词或补充文档。

#### 5.4.5 对话链路中的双检索设计

在对话场景中检索发生两次、形成互补：第一次是“预检索”，上下文组装器在调用对话智能体前按用户原始问题执行一次混合检索，将结果作为初始证据注入提示，使模型第一轮决策即有依据；第二次是“智能体检索”，模型在循环中将知识检索作为工具调用，对查询词改写并按不同资料连续补查，基于多轮结果交叉验证。预检索保证响应效率，智能体检索保证复杂问题的检索深度。

#### 5.4.6 召回测试与索引重建

为支持检索质量诊断，系统提供召回测试：输入测试查询后返回各候选块的得分明细（向量分、关键词分、融合分、重排分与最终排名）与来源信息，并保存运行记录。调整切分参数或嵌入模型后，可通过索引重建接口按新配置清理并重新处理全部知识文档；重建按仓库执行，只处理本仓库数据，不影响其他仓库。

### 5.5 上下文管理与记忆系统

本小节从分层上下文预算、压缩触发机制、会话封存与项目记忆以及候选记忆管理四个方面介绍系统的上下文与记忆设计。

#### 5.5.1 分层上下文预算

长会话的关键矛盾是“历史信息价值”与“上下文窗口容量”之间的权衡。系统将输入预算（默认 24000 tokens，另预留 3000 tokens 给模型响应）划分为五个区块：系统提示 12%、记忆摘要 22%、检索证据 34%、近期对话 22%、工具结果 10%，如图5-4所示。各类信息按额度裁剪：证据按排名截断、工具结果按长度压缩、近期对话保留最近若干条；任何一类信息膨胀都不会挤占其他类别的基本额度。此外，相关研究表明语言模型对长上下文中部信息的利用效率低于开头与结尾位置[22]，因此系统对任务约束与证据等关键信息采用固定位置组织。

![图5-4 分层上下文预算分配示意图](figures/fig5-4.png)

#### 5.5.2 压缩触发机制

系统按 token 压力（已用值与预算的比值）分级触发压缩：进入警戒区（阈值 20000）时仅告警并输出诊断信息；进入自动压缩区（阈值 13000）时执行常规压缩——较早轮次总结为摘要（默认目标 1800 tokens），保留最近 8 条消息原文，工具结果结构化压缩（保留关键字段与结论）；进入激进压缩区（阈值 8000）时进一步压缩证据与记忆区块；在手动压缩区（阈值 3000）下执行最大力度压缩。压缩失败时按配置重试，连续失败达到上限（默认 3 次）后降级为直接截断并记录告警；压缩事件与前后 token 估计均记入诊断信息。

#### 5.5.3 会话封存与项目记忆

当会话达到一定长度或用户主动触发时，系统执行会话封存：将对话转录（Transcript）与摘要固化到会话记录，随后由记忆提取流程抽取结构化信息，更新到项目级线程记忆（ThreadMemory）。项目记忆包含摘要、事实、决策、开放问题、任务、用户偏好、仓库上下文与引用等结构化字段；相较于保存原始对话，其 token 占用更小、检索精度更高。后续会话开始时，记忆摘要作为上下文区块注入，使智能体“记得”项目的历史决策与待办事项。

#### 5.5.4 候选记忆与人工批准

并非所有从对话中抽取的信息都值得长期保存，错误结论一旦固化为长期记忆会被反复沿用。系统因此设计“候选记忆—人工批准”机制：提取条目先进入候选记忆表（MemoryCandidate），状态为待审批，附带来源会话与提取依据；用户审查后批准（approved）的条目才进入记忆体系参与后续召回，拒绝条目保留状态以备追溯。召回事件（RecallEvent）记录每次记忆检索的查询、范围、结果与引用，形成记忆使用的完整审计。

### 5.6 安全草稿与审计机制

本小节介绍草稿生命周期、权限校验与审计以及凭据安全三个方面的设计与实现。

#### 5.6.1 草稿生命周期设计

涉及外部系统写操作的能力（发表评论、创建或关闭缺陷、添加标签等）采用草稿机制承接。草稿实体（ActionDraft）包含类型、目标、正文、风险级别、状态、创建人、确认人、执行时间与结果等字段，生命周期为：待确认（pending_confirmation）→ 已确认执行或取消，执行失败时记录错误且可重试。模型产生写操作意图时，先调用安全风险分类工具评估风险级别，再由安全智能体生成草稿正文；草稿以卡片返回对话界面，经用户核对确认后才执行真实写操作。操作草稿与人工确认的整体流程如图5-5所示。

![图5-5 操作草稿与安全确认流程图](figures/fig5-5.png)

#### 5.6.2 权限校验与审计

系统实现角色-动作维度的权限校验模块，在草稿确认执行与关键管理接口上强制校验当前用户的角色权限（如普通成员不允许执行关闭缺陷等高权限操作）。所有写操作与关键管理操作（同步、索引重建、草稿执行等）写入审计日志表（AuditLog），记录操作者、操作类型、目标对象、请求参数摘要、执行状态与结果，形成“谁在何时对什么执行了什么、结果如何”的完整记录链，满足事后审计与问题追溯需求。

#### 5.6.3 凭据安全

代码托管平台令牌等敏感凭据在持久化时使用对称加密存储（加密密钥由环境变量提供），接口返回时只回传“已配置/未配置”状态而不回传明文；日志系统在输出前对已知敏感字段做脱敏处理。环境变量为凭据的唯一推荐入口，开发演示模式下默认关闭真实写操作。

### 5.7 流式进度推送与运行轨迹

本小节介绍流式事件流设计与运行轨迹持久化两个部分。

#### 5.7.1 SSE 事件流设计

对话与工作流执行时间较长，系统采用 SSE 持续推送执行事件，事件类型覆盖全过程：运行开始与路由决策、模型决策摘要、工具调用开始与结束、工作流任务计划与状态变化、答案文本分片、引用列表与运行结束。前端按事件类型分别渲染到“执行轨迹”与“回答内容”两个区域，用户可以看到系统“正在做什么”，而不是面对长时间无响应的界面，整体时序如图5-6所示。SSE 相比 WebSocket 实现更简单、对服务端更友好，且天然支持断线重连，符合“服务端单向推送进度”的通信模式。

![图5-6 流式推送与运行轨迹时序图](figures/fig5-6.png)

#### 5.7.2 运行轨迹持久化

系统的每次执行都在三个粒度留下持久化轨迹：对话运行（AgentRun）记录单次对话的用户消息、路由、完整工具调用序列与最终回答；工作流运行（AgentWorkflowRun）记录目标、规格、观察报告、最终结论与指标；任务运行（AgentTaskRun）记录每个任务的输入、结果、状态、错误与起止时间。三层记录通过外键关联，形成一个完整可回放的分析过程。当回答质量出现问题时，可以沿轨迹逐层检查：是工具参数有误、检索证据不足、任务结论冲突，还是综合阶段的组织问题，从而将“回答不好”这一模糊现象定位为具体环节的具体缺陷。

### 5.8 能力扩展机制

本小节介绍基于 MCP 的外部工具接入与技能运行时两种扩展机制。

#### 5.8.1 基于 MCP 的外部工具接入

系统通过模型上下文协议（MCP）接入外部工具服务。MCP 定义了一套标准化的工具描述与调用协议，系统内部的 MCP 客户端负责连接外部服务、拉取工具清单并适配到统一的工具注册表；记忆服务即以 MCP 服务形式提供，使记忆工具的实现在协议层与其他工具解耦，可独立部署与升级。

#### 5.8.2 技能运行时

对于需要固定步骤与规范的稳定流程（如缺陷分诊、构建排障、安全草稿、周报等），系统实现了技能运行时（Skill Runtime）。每个技能以 SKILL.md 文件定义，包含适用条件、执行步骤、工具白名单与输出规范；运行时按用户显式指定或触发条件激活技能，激活时校验技能声明的工具是否可用，执行期间只加载当前技能的指令与受限资源；技能名称、版本、激活原因与校验结果记入运行轨迹。系统内置六类技能：缺陷分诊、合并请求审查、构建排障、项目调查、安全草稿与周报。技能机制把“提示词工程实践”沉淀为可版本化、可审计、可复用的资产。

### 5.9 前端界面实现

前端应用基于 Next.js 15 的 App Router 组织页面，使用 React Query 管理服务端状态与缓存。主要页面包括：仓库页（接入、同步与健康摘要）、对话页（流式对话与执行轨迹）、缺陷页与合并请求页（列表与单条分析）、持续集成页（运行列表与排障）、工作流记录页（工作流回放）、知识库页与详情页（文档管理与召回测试）、检索问答页、代码图页、草稿页（草稿审查与确认）、评测页（提交、进度与结果对比）以及报告页、工作区页等，共十七个路由页面。

交互上实现三个要点：其一，流式渲染，对话接口以事件流读取，答案分片与轨迹事件分别渲染，长回答不阻塞界面；其二，异步任务，评测等后台任务提交后以轮询跟踪进度，刷新或关闭页面不中断任务；其三，证据可视化，编号引用渲染为可交互的证据卡片，展示来源类型、路径与原文片段，便于核对结论依据。

### 5.10 本章小结

本章介绍了系统各模块的设计与实现：数据接入模块实现五类数据的分页同步、五态状态管理与仓库健康检查；对话智能体基于状态图实现工具调用循环与三重执行约束；多智能体工作流实现四角色协作、依赖驱动的并行调度与有限重规划；检索模块实现数据分流、结构感知切分、双路召回、加权融合、重排引用与召回测试；上下文与记忆模块实现分层预算、分级压缩、会话封存与候选记忆人工批准；安全模块实现草稿生命周期、权限校验与审计留痕；此外还包括流式推送、运行轨迹、MCP 与技能扩展及前端实现要点。

| T6 | 构建失败排障 | 选取失败运行记录执行排障分析 | 提取关键错误块，给出失败类型、原因分析与排查步骤 | 符合预期 |
| T7 | 多智能体工作流 | 提出“检查缺陷、合并请求与失败构建，判断版本能否发布”问题并确认计划 | 生成计划，按依赖并行执行各任务，输出观察发现与汇总结论，全过程可回放 | 符合预期 |
| T8 | 检索问答与引用 | 在已上传知识库上执行问答并核对引用 | 回答带编号引用，引用可展开并对应原文；无证据时明确提示而非编造 | 符合预期 |
| T9 | 召回测试 | 对典型查询执行召回测试 | 返回各候选块各阶段分数与排名明细 | 符合预期 |
| T10 | 安全草稿 | 在对话中触发“对合并请求发表评论”意图 | 生成待确认草稿且不直接执行；确认后执行并写入审计日志 | 符合预期 |

### 6.4 基于 RAGAS 的回答质量评估

本小节介绍基于 RAGAS 的评估体系设计，包括评估流程、指标与验收门禁，以及回归对比与失败诊断机制。

#### 6.4.1 评估体系设计

功能测试验证“功能是否可用”，评测体系回答“回答是否变好”。系统建立基于固定评测集的自动评估流程：评测在隔离会话中真实运行生产对话智能体与完整工具集，先收集预检索证据，再由智能体循环执行二次检索，最后统一收集回答、证据与工具轨迹，交由 RAGAS 框架[12]计算质量指标；评测结果持久化评测集哈希、阈值配置、逐题工具轨迹、检索证据、硬规则检查与失败诊断信息，使两次评测具备严格可比性。

#### 6.4.2 评估指标与验收门禁

评测指标分为语义质量指标与执行行为指标两组，各项指标及验收阈值如表6-4所示（阈值可在配置中调整，表中为默认值）。

**表6-4 评测指标与验收阈值**

| 指标 | 含义 | 默认阈值 |
|------|------|---------|
| 上下文精确率（Context Precision） | 检索到的证据中相关内容的占比 | ≥ 0.75 |
| 上下文召回率（Context Recall） | 标准答案所需证据被检索到的比例 | ≥ 0.80 |
| 忠实度（Faithfulness） | 回答内容忠实于检索证据、无编造的比例 | ≥ 0.90 |
| 答案相关性（Answer Relevancy） | 回答与问题的相关程度 | ≥ 0.80 |
| 智能体目标达成度（Agent Goal Accuracy） | 回答是否达成题目定义的预期目标 | ≥ 0.80 |
| 工具调用准确率（Tool Call Accuracy） | 工具调用行为与期望工具使用的一致性 | ≥ 0.90 |
| 工具调用 F1（Tool Call F1） | 工具调用行为的查准与查全综合值 | ≥ 0.90 |

整体通过要求“硬规则全部满足”且“五项语义指标均达到阈值”。硬规则检查确定性行为（如引用是否完整、输出结构是否合法、是否出现禁止内容），语义指标由模型裁判（Judge）评分。评测页面将“执行状态”与“质量状态”分离展示：低分是质量失败；裁判调用失败或指标缺失则属于评测不完整，不能伪装为质量结论，这一区分保证了评测结论本身的可靠性。

#### 6.4.3 回归对比与失败诊断

评测体系服务于持续迭代，设计了四条闭环路径：

（1）回归对比。可选择两个“评测集哈希、裁判配置与 Top-K 一致”的历史评测结果进行对比，逐题展示指标变化与证据差异，回答“改动是否带来真实提升”。

（2）失败诊断。展开问题用例可查看实际回答、参考答案、检索来源、工具轨迹与诊断建议，定位失败环节（检索未命中、工具选择错误、综合表述偏差等）。

（3）评测到工单的闭环。对确认由系统缺陷导致的失败用例，可一键生成“创建缺陷”类型的操作草稿，把失败用例、证据与建议带入人工确认流程，不直接写入平台，形成“评测—诊断—工单—修复—回归”闭环。

（4）评分重试。裁判超时或个别指标缺失时，支持“仅重试异常评分”，复用已保存的回答与证据重新评分，无需重跑对话智能体。

### 6.5 本章小结

本章介绍了系统的测试与评估工作：说明了测试环境配置与四层测试策略；通过十二个代表性功能用例验证了数据接入、分析能力、协作决策、检索问答与安全机制等核心场景；介绍了自动化测试体系；并说明了基于 RAGAS 的回答质量评估设计，包括指标、阈值、回归对比、失败诊断与评测闭环。结果表明，系统各功能实现符合需求定义，具备可量化、可回归的质量保障能力。

## 第7章 总结与展望

本章对全文工作进行总结，并分析系统现存的不足与后续的改进方向。

### 7.1 全文总结

本文针对研发协作中“信息分散、证据收集成本高、复杂判断依赖资深经验”的现实问题，设计并实现了一个基于多智能体协作的研发协作系统。论文完成的主要工作如下：

（1）完成了系统需求分析与总体设计。在可行性与需求分析的基础上，提出了证据驱动、分层解耦、人机协同、安全可控、可观测与可评测五项设计原则，完成了五层总体架构、八个功能模块、数据库域划分与接口协议设计。

（2）实现了研发数据接入与同步模块。支持五类研发数据的分页同步与覆盖范围报告，通过五种同步状态区分完整、为空、部分、失败与跳过情形，并实现部分失败保留策略与定时同步。

（3）实现了基于原生工具调用的对话智能体。通过状态图组织“决策—工具执行—结果观察”循环，实现最大步数、重复调用检测、八类工具错误分类处理与上下文溢出恢复等执行约束。

（4）实现了“规划—调度—观察—综合”多智能体工作流。通过依赖驱动的并行调度、失败跳过、结构化观察检查与有限重规划，支撑跨领域工程决策问题的系统化分析，并持久化工作流级与任务级运行轨迹。

（5）实现了工程化检索增强生成链路。通过研发数据分流区分当前代码、实时状态与历史知识三类数据的访问方式；实现结构感知切分、双路召回、加权融合、重排、编号引用、按仓库隔离、召回测试与答案门禁。

（6）实现了上下文与记忆、安全执行与评测体系。包括分层上下文预算与分级压缩、会话封存与候选记忆人工批准、安全草稿生命周期与审计留痕，以及基于 RAGAS 的量化评估、回归对比与失败诊断闭环。

系统测试与评估表明，各功能模块实现符合设计预期，关键链路具备自动化验证与量化度量能力。本文的工作完整覆盖“数据接入—知识检索—智能体协作—安全执行—效果评测”五个环节，对同类大语言模型应用系统的工程化落地具有参考价值。

### 7.2 不足与展望

受时间与条件限制，本系统仍存在以下不足，也是后续改进的方向：

（1）评测规模有限。当前固定评测集侧重研发问答的核心场景，题目数量与覆盖度仍有提升空间；后续可扩展多类型、多难度的评测集，并引入更细粒度的过程指标。

（2）模型能力依赖。系统分析质量与所接入模型的能力强相关，不同模型在工具调用稳定性与长上下文处理上差异明显；后续可研究模型路由与多模型协同策略，按任务类型选择适配模型，并加强弱模型下的降级路径设计。

（3）写操作自动化程度保守。安全草稿机制保证了安全性，但也使操作链路包含人工确认环节；后续可在风险分级基础上设计“低风险白名单自动执行 + 高风险人工确认”的差异化策略。

（4）多用户与权限体系较简单。当前角色模型以满足演示与单团队使用为主；后续可完善多租户隔离、细粒度权限与团队协作能力。

（5）增量同步与数据规模。当前同步以分页全量拉取为主，随着仓库规模增长，可引入基于时间戳与变更事件的增量同步机制，并结合平台 Webhook 实现近实时更新。

总体而言，本文验证了多智能体架构在研发协作场景中的可行性，也展示了“证据驱动、人机协同、安全可控、可评测”设计思路的工程价值。随着大语言模型能力的持续演进，此类系统有望在研发效能提升中发挥越来越重要的作用。
